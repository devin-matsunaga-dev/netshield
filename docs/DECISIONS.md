# DECISIONS.md — NetShield

> Append-only. One line per decision: what was chosen, over what, why, and which package settled it. A later session treats every line here as already settled and does not relitigate it.

## Format

`chose X over Y because Z (WP-N.N, YYYY-MM-DD)`

## Pre-build decisions

These were settled while writing the steering documents, before WP-0.1.

- Chose a modular monolith over microservices because a single administrator deploying to one on-premises host needs one process tree to reason about, and module isolation is enforceable by architecture test without a network boundary (pre-build, 2026-09-03)
- Chose PostgreSQL with TimescaleDB over a separate time-series database because one store means one backup, one connection pool, and one query language across inventory joins and telemetry, which matters more at 500 devices than the throughput a dedicated TSDB would add (pre-build, 2026-09-03)
- Chose to split push ingest into .NET and pull collection into Python over a single collector runtime because syslog and flow reception is socket and back-pressure work while SNMP and network CLI is protocol-library work, and each ecosystem is clearly stronger at one of them (pre-build, 2026-09-03)
- Chose read-only device access with no write path of any kind for V1 over including config push because blast radius on production network kit is the one mistake that cannot be rolled back from a browser (pre-build, 2026-09-03)
- Chose relational adjacency tables over a graph database because V1 needs one-hop topology and downstream-reachability suppression, not multi-hop traversal, and a graph store is a Phase-2 architecture change if correlation is ever built (pre-build, 2026-09-03)
- Chose to defer all automation, threat intelligence, correlation-graph, and path-analysis work over including a thin version of each because a thin version of a correlation engine is worse than none and would set the architecture before the data model is proven (pre-build, 2026-09-03)
- Chose file-import-only vulnerability data over active scanning or NVD lookups because the platform must run with no outbound internet dependency inside a customer network (pre-build, 2026-09-03)
- Chose self-hosted Inter woff2 over a font CDN for the same reason (pre-build, 2026-09-03)
- Chose the reference dashboard screenshot as the binding visual source of truth over an independently authored design system because the design direction is already settled and re-deriving it invites drift (pre-build, 2026-09-03)

## Build decisions

- Chose the classic `.sln` format over the .NET 10 default `.slnx` because `CONVENTIONS.md` §1 names `NetShield.sln` in the binding repository layout (WP-0.1, 2026-09-03)
- Chose FluentAssertions 7.2.0 over 8.x because v7 is the last Apache-2.0 release and v8 onwards requires a paid licence for commercial use, which this project has not confirmed (WP-0.1, 2026-09-03)
- Chose to keep the `Aspire.AppHost.Sdk` 13.5.3 version literal in `NetShield.AppHost.csproj` over moving it into `Directory.Packages.props` because it is an MSBuild SDK reference rather than a `PackageReference`, and central package management does not govern SDK imports (WP-0.1, 2026-09-03)
- Chose `xunit.v3` over the SDK template's xUnit v2 because the test projects were still empty and the migration cost only ever grows (WP-0.1, 2026-09-03)
- Chose to set `TargetFramework` in `Directory.Build.props` and delete it from every `.csproj` over leaving the template's per-project declarations because `ARCHITECTURE.md` §10 admits one version floor and a project cannot drift from a value it does not state (WP-0.1, 2026-09-03)
- Chose `insert_final_newline = true` over the `dotnet new editorconfig` default of `false` because the repository will also hold TypeScript and Python, where a trailing newline is the universal convention (WP-0.1, 2026-09-03)
- Chose to enforce this package's own "Done when" criteria as tests in `NetShield.ArchitectureTests` over accepting the zero-tests allowance in `WORK_PACKAGES.md` because `CONVENTIONS.md` §7 requires tests and the invariants have to hold for every project added after this one, not just the nineteen created here (WP-0.1, 2026-09-03)
- Chose to check those invariants by parsing the `.csproj` files on disk over inspecting loaded assemblies because MSBuild-level rules are not observable from compiled metadata and the file-based check covers projects nothing references yet (WP-0.1, 2026-09-03)
- Chose to delete the Worker and Hello World placeholders the templates generate over keeping them because WP-0.1 produces an empty skeleton and a stub that logs on a timer is invented behaviour a later package would have to unpick (WP-0.1, 2026-09-03)
- Chose MailPit `v1.31.0` over the MailHog named in the WP-0.2 entry because MailHog was archived upstream in 2024 at v1.0.1 while MailPit is the maintained drop-in for the same SMTP-sink role, and MailPit's `/readyz` endpoint lets the Aspire dashboard report the resource healthy rather than merely running (WP-0.2, 2026-09-03)
- Chose `timescale/timescaledb:2.29.0-pg17` over `timescale/timescaledb-ha` because the Alpine image is the lighter development container and V1 is explicitly single-node with no HA in scope per `SPEC.md` §3 (WP-0.2, 2026-09-03)
- Chose to set `TIMESCALEDB_TELEMETRY=off` on the PostgreSQL container over accepting the image default because the image reports usage to Timescale on a schedule and `ARCHITECTURE.md` §1 permits no outbound internet call at runtime (WP-0.2, 2026-09-03)
- Chose to let the `netshield` database inherit the `timescaledb` extension from `template1` over running an explicit creation script because the image's own init script installs the extension into `template1` before Aspire creates any database, and a second creation path would only be able to diverge from it (WP-0.2, 2026-09-03)
- Chose `/health` for liveness and `/health/ready` for readiness over the Aspire template's `/health` and `/alive` because the WP-0.2 "Done when" names both paths, and the split keeps an unreachable PostgreSQL from being read as a reason to restart the process (WP-0.2, 2026-09-03)
- Chose to register PostgreSQL and Redis client integrations in `Web.Host` in this package over deferring them to WP-0.3 because `/health/ready` has nothing to report on without them, and a readiness endpoint that only reports on itself is not a readiness endpoint (WP-0.2, 2026-09-03)
- Chose to register `NetShield.Ingest` in the AppHost with `AddServiceDefaults()` alone over leaving it out until Phase 4 because an AppHost that models four of the five runtime processes is a misleading picture of the system, and wiring it to stores it does not yet use would pull Phase 4 work forward (WP-0.2, 2026-09-03)
- Chose to keep every WP-0.2 test container-free over automating the "Done when" criteria against a live stack because `dotnet test` should stay deterministic and runnable without a Docker daemon; container-backed tests arrive as a separate suite when `CONVENTIONS.md` §7's Testcontainers harness lands in WP-0.3 (WP-0.2, 2026-09-03)
- Chose to enforce "no hardcoded connection string" as two repository-wide architecture tests — a scan of every `appsettings*.json` for a `ConnectionStrings` section and a scan of every `src` string literal for a host, credential or store URI — over trusting review because the rule in `SPEC.md` §5 has to hold for every package that follows, not just this one (WP-0.2, 2026-09-03)
- Chose to reject a `limit` above 200 with a 400 over clamping it silently because a caller who asks for 5,000 rows and receives 200 reads the response as "there were only 200", which is a data-loss bug wearing a pagination costume (WP-0.3, 2026-09-03)
- Chose to apply secret redaction by replacing `ILoggerFactory` over decorating each `ILoggerProvider` because a provider-level decorator covers only the providers registered when it ran and silently stops covering the next one somebody adds, which is the failure mode `ARCHITECTURE.md` §8 exists to rule out (WP-0.3, 2026-09-03)
- Chose to forward a log line unmodified when it holds no secret over always rebuilding its state because an untouched line then keeps its alignment and format specifiers and its values keep their types for structured sinks, and only a line that actually carried a secret pays the cost (WP-0.3, 2026-09-03)
- Chose to redact log state, scopes and the rendered message but not the attached `Exception` because rewriting an exception would alter the stack trace an operator needs, and a credential inside an exception message is a bug at the throw site rather than something a sink can repair (WP-0.3, 2026-09-03)
- Chose to resolve an outbox row's event type through an explicit `IntegrationEventRegistry` over `Type.GetType(string)` because a stored string must never be able to choose which type gets constructed, and an event nothing can resolve then fails at the publish rather than writing a row that could only ever fail (WP-0.3, 2026-09-03)
- Chose to leave a repeatedly failing outbox row parked and unprocessed after `MaxAttempts` over deleting it or marking it delivered because a poison message has to stay visible to an operator, and the dispatcher skipping it costs one indexed predicate (WP-0.3, 2026-09-03)
- Chose to keep delivered outbox rows over deleting them on delivery because they are the record of what the system told itself, and pruning belongs to the retention policy rather than to the dispatcher's hot path (WP-0.3, 2026-09-03)
- Chose exponential backoff from the poll interval to `MaxPollInterval`, logging `Error` on the first failure of a run and `Warning` on the ones that follow, over an error per poll because an unreachable database would otherwise produce one `Error` a second for as long as the outage lasted (WP-0.3, 2026-09-03)
- Chose to make `AddOutboxDispatcher` a separate opt-in call over registering the dispatcher inside `AddNetShieldPlatform` because the outbox claims rows without `FOR UPDATE SKIP LOCKED` — correct for the single-node V1 in `SPEC.md` §3 — so exactly one process may dispatch, and that has to be a deliberate choice at the composition root (WP-0.3, 2026-09-03)
- Chose `EFCore.NamingConventions` for `snake_case` over naming every column by hand in each EF configuration because `CONVENTIONS.md` §3 applies to every table in the system and a convention that must be remembered per property is one that will eventually be forgotten on one (WP-0.3, 2026-09-03)
- Chose to register the exception handler in every environment over letting the developer exception page render in Development because `SPEC.md` §5 carves out no environment for a stack trace, and a response shape that differs between Development and Production is one nobody tests (WP-0.3, 2026-09-03)
- Chose not to place the caught exception on the `ProblemDetailsContext` over passing it for a customization to read because anything reachable there could be serialised, and a 500 must carry no message, no type name and no stack trace (WP-0.3, 2026-09-03)
- Chose to replace `Aspire.Npgsql` with `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` in `Web.Host` over registering both because the outbox needs `PlatformDbContext` and keeping the raw data source alongside it would contribute a second, redundant PostgreSQL readiness check (WP-0.3, 2026-09-03)
- Chose to enforce the `ARCHITECTURE.md` §4 module rules over the `.csproj` reference graph over a reflection-based rule library because a reference an empty project declares is elided from assembly metadata, so an assembly-level rule would pass over all ten still-empty modules and report confidence it does not have; a rule library earns its place in WP-1.1 (WP-0.3, 2026-09-03)
- Chose to enable `CentralPackageTransitivePinningEnabled` and lift `Microsoft.Extensions.Hosting` to 10.0.11 over letting each project resolve its own transitive EF Core version because the provider, the naming convention and the design-time tooling each wanted a different patch of `Microsoft.EntityFrameworkCore.Relational` and the build was picking whichever one a given project saw first (WP-0.3, 2026-09-03)
- Chose to mark `**/Persistence/Migrations/*.cs` as generated code in `.editorconfig` over reformatting each migration by hand because `dotnet ef migrations add` writes a BOM and its own layout, `CONVENTIONS.md` §3 forbids editing a migration after it merges, and otherwise every generated migration would fail the style gate on the day it was created (WP-0.3, 2026-09-03)
- Chose to give each integration test its own database on one shared container over sharing a database across the class because every one of these tests writes to the same outbox table, and a test that owns its database cannot be affected by the order the others ran in (WP-0.3, 2026-09-03)
- Chose `Konscious.Security.Cryptography.Argon2` 1.3.1 over `Isopoh.Cryptography.Argon2` because .NET ships no Argon2 at all, both are MIT, and Konscious exposes the raw parameters NetShield needs to encode into the stored hash rather than a fixed format of its own (WP-0.4, 2026-09-03)
- Chose to store every password as a PHC string — `$argon2id$v=19$m=,t=,p=$salt$digest` — over storing the digest alone because a column holding only the digest can never be re-costed without invalidating every password in it, and the parameters travelling with the hash are what make rehash-on-sign-in possible (WP-0.4, 2026-09-03)
- Chose the OWASP Argon2id parameters `m=19456 KiB, t=2, p=1` with a 128-bit salt as the configurable default over a heavier fixed cost because they are the published floor for this variant and an operator on faster hardware can raise them without a code change or a lockout (WP-0.4, 2026-09-03)
- Chose to answer an unknown username, a wrong password, a disabled account and a locked-out account with one identical 401 over distinguishing them because WP-0.4 requires no user enumeration, and to record the distinction in the log where an operator can see it and a caller cannot (WP-0.4, 2026-09-03)
- Chose to verify a presented password against a decoy hash when the username matches no account over returning as soon as the lookup misses because a 401 that arrives tens of milliseconds early enumerates the user table just as surely as a different error message would (WP-0.4, 2026-09-03)
- Chose two cookies — a short-lived session cookie on `/` and a refresh cookie scoped by `Path` to `/api/v1/auth/refresh` — over one long-lived cookie because the credential presented on every request should be the one worth the least, and the browser then never sends the refresh token to any other endpoint (WP-0.4, 2026-09-03)
- Chose `SlidingExpiration = false` on the session cookie over letting it slide because the refresh token is what extends a session and it rotates, whereas a sliding cookie would extend one indefinitely with nothing to detect a theft by (WP-0.4, 2026-09-03)
- Chose to fix `HttpOnly`, `Secure` and `SameSite=Lax` in code with no configuration binding over making them settable because ARCHITECTURE.md §8 requires all three, and a security property an environment file can turn off is one that will eventually be off in production (WP-0.4, 2026-09-03)
- Chose to revoke the entire refresh-token chain when a already-spent token is presented over revoking only that token because replaying a spent token is the signature of a stolen cookie, and signing out the legitimate holder too is the intended outcome when one of the two holders is an attacker (WP-0.4, 2026-09-03)
- Chose to store only the SHA-256 digest of a refresh token, unsalted, over an Argon2id hash because the input is 256 bits this process generated rather than something a person chose, so there is no candidate list to run against it and no reason to pay a memory-hard cost on every refresh (WP-0.4, 2026-09-03)
- Chose to clear the failure counter when a lockout is applied over leaving it at the maximum because a lapsed lockout should return the account to a full allowance rather than locking again on the next single mistake (WP-0.4, 2026-09-03)
- Chose to answer a wrong *current* password on the change-password endpoint with 422 over 401 because the session is perfectly valid, and WP-0.7 makes a 401 anywhere redirect to sign-in — so a typo would otherwise sign the user out (WP-0.4, 2026-09-03)
- Chose to revoke every other session on a password change and re-issue the caller's own over leaving the other sessions signed in because a password change is what someone does after suspecting their password is known (WP-0.4, 2026-09-03)
- Chose to source the first-run administrator's password from configuration, supplied by a persisted Aspire secret parameter, over shipping a default or generating one and printing it because a shipped default is a shipped vulnerability and SPEC.md §5 does not allow the log to be where a credential is read from (WP-0.4, 2026-09-03)
- Chose to seed only when the `users` table is empty, and to refuse a seed password the policy rejects, over seeding by username or exempting the seed from the policy because an installation whose administrator was deleted has a recovery problem rather than a seeding one, and the one account that administers the system must not be the one account exempt from its rules (WP-0.4, 2026-09-03)
- Chose to give `IdentityDbContext` its own migration history table `__ef_migrations_history_identity` over sharing EF's default with `PlatformDbContext` because independently migrated contexts should each be able to say what they have applied without reading rows written by the other (WP-0.4, 2026-09-03)
- Chose to store `UserRole` as its name in the database and serialise it as its name on the wire over its ordinal because adding a role in WP-0.5 would otherwise renumber every row and every stored response that already meant something else (WP-0.4, 2026-09-03)
- Chose to keep `SessionGrant` out of `IdentitySerializerContext` over marking its members ignorable because an endpoint that returned it by mistake then fails on the first request rather than shipping a refresh token in a response body (WP-0.4, 2026-09-03)
- Chose to hold cookies by hand in the integration-test client over using `CookieContainer` because a `CookieContainer` will not replay a `Secure` cookie over the test host's plain HTTP, and the raw `Set-Cookie` header is where `HttpOnly`, `Secure` and `SameSite` can actually be asserted (WP-0.4, 2026-09-03)
- Chose to replace the cookie handler's redirect events with problem-details responses over accepting its `302` to a sign-in page because CONVENTIONS.md §4 gives the API one error shape and its only client reads status codes (WP-0.4, 2026-09-03)
