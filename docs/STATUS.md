Branch: `feat/wp-2.4-topology-ui`

The React Flow canvas per `DESIGN.md` §6: dot grid, 48px node tiles with state-encoded borders, zoom and fit controls stacked top-left, the legend in the card header, a node click opening device detail. It closes Phase 2, and it is the package that first makes any of Phase 2 visible — WP-2.1, WP-2.2 and WP-2.3 have between them built three walks, four tables and nine routes, and nothing a person uses reaches any of them.

**It touches UI, so `DESIGN.md` and `docs/design/reference-dashboard.png` are both required reading** — both, not one, per `SESSION.md` §1. The reference screenshot's topology card is the target and §9 admits no invented visual direction.

Everything it draws now exists. `GET /api/v1/topology/graph` returns nodes with `state`, `rank` and `x`/`y`, edges with `confidence` and the two `included` flags, the component list, and the geometry the coordinates are in — so the canvas can render without a layout pass. **The coordinates are usable as they are, and the ranks are there if WP-2.4 would rather run `dagre` itself**; that was settled deliberately so the choice would not need a contract change either way. `TopologyGraphLayout` is the geometry to draw at, and it is `DESIGN.md` §6's node tile rather than a number invented here.

Three things from WP-2.3 are worth knowing before starting. **A page is 200 nodes**, so a 500-node estate is three requests and the canvas has to accumulate pages — an edge arrives with the earlier of its two endpoints and says on `aDeviceIncluded`/`bDeviceIncluded` whether the far end is on the page yet, which is what lets the canvas draw what it has. **A component is an island**, ordered largest first, and the "disconnected component rather than dropped" criterion means the canvas will really be handed islands to place. And **a node is a device**: an edge to an unmanaged switch or an LLDP-speaking server is `externalEdgeCount` on the node rather than a tile, so a device can show more links than it has drawn edges, and the canvas should say so rather than looking wrong.

The two "Done when" criteria beyond the visual match are a performance one and an accessibility one — 500 nodes panning and zooming at 60fps, and the canvas keyboard navigable with a table fallback. Neither is served by anything that exists; the table fallback in particular is a second rendering of the same data and should read the same query rather than a second one.

- **WP-2.3 — Topology graph API** (2026-09-09, `feat/wp-2.3-topology-graph`). The third package of Phase 2 and the first read in the build with a number attached to it. One route, `GET /api/v1/topology/graph`, on `TopologyRead` — **no RBAC change**, since that permission's own definition already reads "the topology graph and the VLAN inventory" — and **no table, no migration, no walk, no schedule and no subscriber**: it is a read over what WP-2.1 and WP-2.2 concluded, and `git status` over `src/netshield-collector` is empty. **The multi-hop question was put to the human and answered**: `ARCHITECTURE.md` §1 says to stop and ask, the WP entry names "depth from a root", and the walk was confirmed in scope *limited strictly to graph rendering* — root plus explicit depth and node ceilings, reading `device_adjacencies`, with no reachability, blast-radius, path-analysis or what-if semantics. That boundary is stated on the handler, on the contract and in `DECISIONS.md` rather than only here. **The bounding is two explicit ceilings**: `MaxGraphDepth` of 10 and `MaxGraphNodes` of 2,000, four times `SPEC.md` §1's estate, and a graph cut by the second says so on `truncated` rather than quietly returning less. The walk is a loop of at most ten bounded queries rather than a recursive CTE, so the bound is somewhere a reader can see. **A filter restricts the walk and not just the answer** — depth is measured through devices the site and VLAN filters admit, because "one hop through VLAN 20" and "one hop through anything, then discard" differ exactly where an operator would be surprised. The VLAN filter is a join through `GetVlanListHandler.LiveRows` and not a new read, and the site filter is the device list's `ILike`, so two screens cannot disagree about which devices are at a site. **`GraphLayoutRule` is the decomposition and the layout as one pure function**, the `AdjacencyRule` and `VlanAggregationRule` shape: connected components, breadth-first ranks from each island's own root, barycentre ordering within a rank, then coordinates from `DESIGN.md` §6's node tile. **No dependency — there is no `dagre` for .NET** — and the response carries the rank and the geometry beside the coordinates, so WP-2.4 can run the real one later without the contract changing. **"Paginated by subgraph" is the node ordering: component, then rank, then device id**, largest island first with the root breaking the tie, and the cursor is that triple; the drawing order within a rank is deliberately not in the key, because a barycentre position moves when a node elsewhere does. **An edge arrives with the earlier of its two endpoints** and carries `aDeviceIncluded`/`bDeviceIncluded`, so no edge is dropped for straddling a page and none arrives twice. **A node is a device**: an edge to an unmanaged switch or an LLDP-speaking server is `externalEdgeCount` on the node rather than a tile with no facts behind it, and the edge itself is still in full on the device's own adjacency route. The 200-row page cap stands — no graph-specific exception — so the "500 nodes under 500 ms" criterion is measured as **the whole estate fetched page by page, end to end**, three requests each recomputing the whole graph: 77 ms on the machine this was written on. 57 new tests: 46 unit (the layout as arithmetic — islands, roots, ranks, crossing reduction, determinism under reordered input — the cursor and its ordering, and the query bounds) and 33 integration over the real round trip against real PostgreSQL, including all three "Done when" criteria. `TopologyGraph` is registered in `InventorySerializerContext`, which WP-2.1's and WP-2.2's shapes are not — see the note below. No frontend change beyond the regenerated `schema.d.ts`.

- **WP-2.2 — VLAN inventory** (2026-09-09, `feat/wp-2.2-vlan-inventory`). The second package of Phase 2 and the smallest: one more SNMP table set, one more table, and the aggregation. **A third topology walk**, at the human's instruction: `walk: "vlans"` reads Q-BRIDGE-MIB's `dot1qVlanStaticTable` — the only standard table carrying a VLAN's *name* — falling back to `dot1qVlanCurrentTable` only where the static one produced nothing, the shape `arp.py` and `bridge.py` already had. It is a `Discover` discriminated on the same `walk` member as WP-1.5's `snmp`, WP-1.6's `sweep`, WP-1.8's `clients` and WP-2.1's `neighbors` and `routes`, so the collector's wire contract is untouched: no `CollectorJobKind` member, no field on the lease, result or heartbeat. It runs on the slowest clock of the three — an hour by default, four times the neighbour interval — because a VLAN is a design decision rather than a cable. **Membership is a bitmap over bridge ports**, so it takes the same `dot1dBasePortTable` hop WP-1.8's forwarding read makes, reusing `bridge.parse_base_ports` rather than making a second join that could disagree; a bit the base-port table cannot place is counted in `unresolvedPortCount` and dropped, because a port number means nothing outside the bridge that issued it. **The `PortList` has two spellings and both had to work**: `session.decode` renders an octet string as hex when any byte is unprintable and as text when none is, so a bitmap of ports 2 and 3 is the single byte `0x60` and arrives as the printable character `` ` ``. `_octets` is `decode` read backwards — hex only where the hex reading could not itself have been written as text — and `test_port_list_reads_back_whatever_decode_wrote` pins it by round-tripping real bitmaps through the real `decode` rather than against a chosen constant. **One table and no conclusion table beside it**, which is the one place this departs from WP-2.1's shape: `device_vlans` is the observation, and the estate-wide view is a grouping of it plus two joins, computed on read. A VLAN summary is cheap derived state and its client count joins the open `client_port_bindings` WP-1.8 writes, which move every time somebody unplugs a laptop — a stored copy could only ever be a stale one needing invalidation from another feature's subscriber. **`VlanAggregationRule` is the merge as one pure function**, the `AdjacencyRule` shape: the identity is the VLAN id alone (a single estate, `SPEC.md` §1), membership is *summed* rather than unioned because a port belongs to exactly one device, and the name is chosen deterministically — most-used spelling, ties broken alphabetically, case not counted as a disagreement, a device that named nothing not voting — with `NameDisputed` surfacing a real disagreement rather than hiding it or splitting the VLAN. **An absence withdraws, as it does for a neighbour table**, and only a reading that was supported *and* untruncated may say so. Four endpoints: `GET /api/v1/vlans` (cursor-paginated, keyed by VLAN id), `GET /api/v1/vlans/{vlanId}` (the aggregate plus every switch carrying it), `GET /api/v1/devices/{id}/vlans` and `POST /api/v1/devices/{id}/vlan-walk` — **no RBAC change**, since `TopologyRead`'s own definition already reads "the topology graph and the VLAN inventory". `RecordVlanWalkResultHandler` is the seventh `CollectorJobCompleted` subscriber and `DeviceVlansChanged` publishes only when the VLAN *set* moved, not when a port was added to a VLAN the device already carried. 121 new tests: 52 collector (both tables, the bitmap in both spellings, the bridge-port join and the executor, against five hand-authored VLAN fixtures), 27 unit (the merge as arithmetic, the payload shapes and the cursor), 41 integration over the whole round trip against real PostgreSQL — including both "Done when" criteria, one of which builds the reference dashboard's literal estate of 45 switches and 360 clients and asserts 12 / 245 / 32 / 83 / 45 — and 1 architecture. No dependencies: Q-BRIDGE is more OIDs over the `pysnmp` session already in place. No frontend change beyond the regenerated `schema.d.ts`.

- **WP-2.1 — Neighbor collection and adjacency** (2026-09-09, `feat/wp-2.1-neighbor-collection`). The first package of Phase 2, and the first that reads vendor-variable tables in bulk. **Two walks, not one**, at the human's instruction: `walk: "neighbors"` reads LLDP and CDP, `walk: "routes"` reads the routing table, and they are separate jobs with separate schedules because a routing table is orders of magnitude larger and less predictable than a neighbour table — a device that answers its neighbour protocols and then times out reading forty thousand routes must not have the edges it already established discarded. Both are `Discover` rows discriminated on the same `walk` member as WP-1.5's `snmp`, WP-1.6's `sweep` and WP-1.8's `clients`, so the collector's wire contract is untouched: no `CollectorJobKind` member, no field on the lease, result or heartbeat. **The vendor decides which protocols to ask for**: `VendorAdapter` gains `neighbor_protocols`, the two Cisco adapters declare CDP and nobody else does, and `NeighborProtocolParityTests` pins that list to `NeighborSource` across the two repositories the way `VendorParityTests` pins the vendor list. **`lldpLocPortNum` is not an `ifIndex`** and the join is the part most likely to break against a real agent, so `collector/snmp/ports.py` reads `ifDescr` and `ifName` as two column walks and `resolve_local_ports` tries three routes in order — the port id naming an interface, a numeric port id that is a known index, then the port number itself, never an index the device did not itself report. The three fixture switches each resolve by a different one of the three. **Three tables behind `Inventory_AddAdjacency`**: `device_neighbors` (what each protocol said, one live row per device, source, port and far end), `device_adjacencies` (what NetShield concluded, one row per edge) and `device_topology_scans` (the per-device schedule and idempotency row, with its own due time, last-applied job and error for each of the two walks). **An absence here *is* evidence, unlike WP-1.8's** — an LLDP table is the device's complete current statement and its agent expires its own entries — so a successful, untruncated reading withdraws what it no longer contains, which is the "a removed link ages out" criterion. Only a protocol that was *supported and not truncated* may withdraw anything: this is the first package to act on flags every walk payload has carried since WP-1.5 and recorded without using. **Two decisions are pure functions in `AdjacencyRule`**, the `AssetResolutionRule` shape: `Survivors` resolves a conflict on one port by letting LLDP outrank a CDP-only account (a chassis identifier is an identity, a CDP device id is a host name, and WP-1.1 settled that a host name is not one), and `Confidence` reads `Confirmed` from a neighbour protocol seen at both ends, `Probable` from one end or from routing at both, and `Possible` from a routing next hop alone. **Endpoints are canonically ordered so both devices' walks converge on one row** — which is what makes the three-switch estate's edge set two edges and not four — and the swap happens only where the far end is a device *and* its port resolved against the interface inventory, because canonicalising on a device id alone would collapse a two-cable aggregate into one link. `ObservedFromA`/`ObservedFromB` and the per-side source lists are what let one switch going quiet downgrade a link rather than delete it. Four endpoints: `GET /devices/{id}/adjacencies` (cursor-paginated, with the per-protocol evidence beside each edge) and `GET /devices/{id}/topology-scan` on `TopologyRead`, and `POST /devices/{id}/neighbor-walk` and `/route-walk` on `DiscoveryRun` — **no RBAC change**, since `TopologyRead`'s own definition already reads "the topology graph and the VLAN inventory". `TopologySchedulePass` is the fourth producer of collector work with its own opt-in registration, and `RecordNeighborWalkResultHandler` and `RecordRouteWalkResultHandler` are the fifth and sixth `CollectorJobCompleted` subscribers. `DeviceAdjacencyChanged` is published only when the edge set actually changed. 219 new tests: 104 collector (LLDP, CDP, the routing tables, the port join and both executors, against nine hand-authored topology fixtures), 43 unit (the two rules as arithmetic, the two identity keys, the payload shapes and the cursor), 66 integration over the whole round trip against real PostgreSQL — including all three "Done when" criteria — and 6 architecture. No dependencies: LLDP, CDP and the three route tables are more OIDs over the `pysnmp` session already in place.

- **WP-1.8 — Client tracking and time-accurate IP resolution** (2026-09-08, `feat/wp-1.8-client-tracking`). The client entity, its history as closed intervals, `ResolveAssetAt`, and the Clients screen WP-1.7 left as a placeholder. **Four tables behind `Inventory_AddClients`**: `clients` (one row per MAC, which is the identity — an address is a lease and a port is a cable), `client_ip_bindings`, `client_port_bindings` and `device_client_scans`. **The interval invariants are indexes, not conventions**: a partial unique index over `ip_address WHERE observed_to IS NULL` makes two open bindings for one address impossible to write, so a handler that failed to close the previous holder fails its insert rather than producing an address that resolves to two clients — and every close is stamped at exactly the successor's open, so the intervals abut with no gap and no overlap. The port index is unique per *client and device* rather than per client, because a MAC is learned by every bridge on the path to it and a per-client rule would have each walk close another switch's correct observation. **The rule that decides what a binding means is that an interval closes only when a conflicting observation supersedes it** — an ARP cache ages an entry out after hours and a forwarding database after minutes whether or not the host is still there, so closing on absence would give an ordinary laptop dozens of intervals a day, each a gap in which resolution answers *unresolved* for an address that never changed hands. **`walk: "clients"` is the third `Discover`**, beside WP-1.5's `snmp` and WP-1.6's `sweep`, with the collector's wire contract untouched: `collector/snmp/arp.py` reads `ipNetToPhysicalTable` falling back to `ipNetToMediaTable`, `collector/snmp/bridge.py` reads `dot1qTpFdbTable` falling back to `dot1dTpFdbTable` and joins the bridge port back to an `ifIndex` through `dot1dBasePortTable`, and both report *whether the device answered the table at all* — a router implements no forwarding database and an access switch no neighbour cache, and treating either absence as "nobody is attached" would be reading silence as a statement. `RecordClientWalkResultHandler` is the fourth `CollectorJobCompleted` subscriber and `ClientSchedulePass` the third producer of collector work. **`IAssetResolver` is internal to the module**, in the shape the credential resolver has been since WP-1.2, with `AssetResolutionRule` extracted as one pure function so the decision that matters is tested as arithmetic. It is cached in Redis **keyed by address** — which is what WP-1.1 wrote `DeviceUpdated.PreviousPrimaryIpAddress` for — over a new `ICacheStore` in `NetShield.Platform` whose null implementation is a legitimate configuration rather than a stub, and the suite runs the resolution tests against both so the two cannot come to different answers. Six endpoints under `InventoryRead`, which already read "devices, *clients*, sites" and so needed no RBAC change, plus `POST /devices/{id}/client-walk` on `DiscoveryRun`. On the SPA: `/clients` with a virtualized ARIA grid, four composing URL-state filters and the resolve panel that is how a person checks a handover by hand, and `/clients/{id}` in three tabs — overview, address history, port history. 227 new tests: 61 unit, 60 integration over the whole round trip against real PostgreSQL and real Redis, 36 collector, and 70 frontend across six suites including seven `axe` passes. Two dependencies: `StackExchange.Redis` (already transitively present) and `Testcontainers.Redis`. Two things were removed rather than shipped: `AssetResolution` carries no observation source, because a nullable enum member makes ASP.NET Core append `null` to the *shared* enum schema and every other shape using it then reads as nullable in the generated client; and the client row carries no `multicast` flag, because a group address is dropped where an observation is read and the column could only ever have been false.

- **WP-1.4 — ICMP reachability and device state** (2026-09-04, `feat/wp-1.4-icmp-reachability`). **The collector queue has a producer and `CollectorJobCompleted` has a subscriber** — the two seams WP-1.3 shipped empty are now closed by the same package that fills them. `collector/icmp/` is three layers with nothing shared between them: `packet.py` is RFC 792 and RFC 4443 as functions from bytes to bytes (checksum, echo request, reply parsing, IPv4 header stripping) and opens no socket; `probe.py` opens one and times what comes back; `executor.py` is the first `JobExecutor` and answers for `Poll` jobs whose parameters name the ICMP probe. **No new dependency and no change to the WP-1.3 wire contract**: no `CollectorJobKind` member, no field on the lease, result or heartbeat. What WP-1.4 fills in is the `parameters`/`data` documents WP-1.3 deliberately left opaque, discriminated by a `probe` member so that a Phase 3 SNMP `Poll` row and a Phase 1 ICMP `Poll` row can tell each other apart in one table. The socket is `SOCK_DGRAM`/`IPPROTO_ICMP` first and `SOCK_RAW` second, and if neither opens the job **fails** naming `ping_group_range` and `CAP_NET_RAW` rather than reporting loss. **A collector failure is never evidence about a device**: a probe that ran and heard nothing is a *successful* job at 100% loss, while a probe that could not be performed is a *failed* job recorded on the reachability row's `last_error` with the device's state and its run of observations untouched — otherwise one process losing a capability would take five hundred devices offline and the alert would name the wrong thing. `device_reachability` (migration `Inventory_AddDeviceReachability`) is a table of its own rather than columns on `devices`, because a counter that changes every sixty seconds has no business touching the row the device list sorts by `updated_at`; `devices.state` stays the published state and is written only on a transition, and a transition deliberately does not stamp `devices.updated_at`. The state machine is one pure function: classify a probe as Online (no loss), Warning (some) or Offline (all), then adopt it only after `SuccessThreshold`/`FailureThreshold` consecutive identical observations — which is why a flapping device emits **no** transition at all rather than one per probe, and why a week-long outage is one `DeviceStateChanged` and not ten thousand. The result handler is idempotent by `last_applied_job_id`, because outbox delivery is at-least-once and a redelivered probe would otherwise advance a run halfway to a threshold only one probe supports. `ReachabilitySchedulePass` queues one probe per due device and stamps the next due time in one transaction through the new enlisting form of `ICollectorJobQueue` — the gap WP-1.3 left for "the first package that actually needs it" — skips any device with a probe still outstanding so a collector outage cannot build a backlog nobody will run, and spreads the next due time by a device-derived offset under one scan so an estate imported in one go does not fall due in one second for ever. `ReachabilityScheduler` is opt-in from the composition root for the reason `AddOutboxDispatcher` is: exactly one process schedules the estate, and the schema step registers the same module. 919 tests: 722 backend (425 unit, 256 integration, 41 architecture), 123 frontend, 74 collector.

- **WP-1.2 — Credential profiles and envelope encryption** (2026-09-04, `feat/wp-1.2-credential-profiles`). ## In flight / noticed

Things spotted during a package that are out of its scope. Do not fix them in the current package — record them here and address them in a package of their own.

- **Nothing draws the graph, and WP-2.4 is the package that closes it.** `GET /api/v1/topology/graph` joins the eight topology routes before it in being reachable over the API and by nothing a person uses. Unlike the others this one has a named owner in the very next package, so it is recorded for completeness rather than as a gap to schedule: the note below about the walk buttons is the part that still has no owner.

- **A node is a device, so an unmanaged switch never appears on the canvas.** WP-2.3 settled that an edge whose far end is not a monitored device is `externalEdgeCount` on the node rather than a tile, because such a far end has no state, no site and no VLAN and none of the graph's filters could match it. The consequence is visible: a switch with an uplink to something NetShield does not monitor shows a degree of 2 and three links, and only the canvas saying so will stop that reading as a missing edge. The information is not lost — `GET /devices/{id}/adjacencies` returns the edge in full — but the graph cannot show it, and the package that decides an external endpoint deserves a tile has to decide what state to draw it in first.

- **The whole graph is recomputed on every page, and 2,000 nodes is where that stops being free.** A component index and a rank are properties of the graph rather than of a row, so each page re-reads the devices and the edges and re-runs the layout. At `SPEC.md` §1's 500 devices the three pages cost 77 ms together and this is measurably simpler than the alternative; at `MaxGraphNodes` it is four times the work over ten pages, and it is also unrate-limited, so a caller paging a large graph in a loop is the cheapest way to make the API do arithmetic. The number to watch is the graph route's p95 rather than any of the ceilings, and the first narrowing would be caching the layout under a key that changes when `DeviceAdjacencyChanged` fires — which is a subscriber, and therefore a package.

- **The graph has no saved layout, and an operator will want to move a node.** The coordinates are computed from the estate on every read, deliberately: a stored arrangement would be a second source of truth about a picture the cabling already determines, and it would go stale the first time a switch was added. What that rules out is pinning — "the core belongs at the top left of *my* map" — which is the first thing anyone asks of a topology canvas. It needs a per-user store and a decision about what happens to a pinned node whose device is removed, and it belongs with the per-user dashboard layout persistence `SPEC.md` §2 puts in Phase 8 rather than with WP-2.4.

- **`InventorySerializerContext` lists a third of the module's contract shapes.** `CONVENTIONS.md` §4 asks for source-generated contexts, and the shapes WP-2.1 and WP-2.2 added — `DeviceAdjacencySummary`, `AdjacencyEvidence`, `DeviceTopologyScanDetail`, `VlanSummary`, `VlanDetail`, `DeviceVlanSummary` and their pages — are not in it. They serialise correctly today, through the reflection-based resolver behind the context, so nothing is broken; what they are not is what the convention asks for, and the gap would become a real one under trimming or AOT. WP-2.3 registered its own `TopologyGraph` rather than leaving a fourth omission, and did not backfill the other six, which would have been six lines of another package's contract in this diff. Whoever next touches those shapes should add them.

- **A `nextCursor` on a graph counts nodes, and a client cannot know how many pages are coming.** `totalNodeCount` and the component list say how big the whole graph is, so a canvas can size its progress, but there is no page count and cannot be one while the limit is the caller's. That is the same shape every cursor-paginated list has and it is worth noting once here because a graph is the first place a reader is expected to accumulate every page before the thing is usable at all.

- **`CredentialProfileCrudTests.Create_ANameALiveProfileHolds_Returns409_EvenInADifferentCase` failed once and has not failed since.** Seen in one full-suite run during WP-2.3 and not in the three that followed, and it passes on its own. Nothing in WP-2.3 touches credential profiles, and every integration test has a database of its own, so the likeliest explanation is contention — that run was the first to have a 500-device seed in it. Recorded rather than dismissed because a test that fails once is a test that will fail again in CI, and the assertion is a status code, which means the interesting information is the body it came with. Whoever sees it next should capture the response before deciding it is environmental.

- **No screen shows a VLAN, and the VLAN walk has no button.** WP-2.2 built four routes and the SPA has no path to any of them: no VLAN tile, no VLAN column on the device screen, no VLANs tab beside Interfaces, and no trigger for `POST /devices/{id}/vlan-walk` — the third walk in a row to ship without one, after WP-1.8's client walk and WP-2.1's two. The reference dashboard's VLAN tiles are Phase 8's widget catalogue and the canvas is WP-2.4's, but a VLANs tab on the device detail is neither of those and would be a small package on its own. `GET /api/v1/vlans` is meanwhile only reachable from a devtools console, which is the state WP-1.9 was created to fix for credential profiles.

- **A VLAN id is treated as estate-unique, and a real network can break that.** WP-2.2 settled that two switches carrying VLAN 20 are carrying one VLAN, which is true of the single estate `SPEC.md` §1 describes and false of two sites that were numbered independently and later joined. The symptom would be a VLAN whose device count is the sum of two unrelated VLANs and whose `nameDisputed` is permanently true; the flag is deliberately the visible half of that. Fixing it means scoping the identity — by site, or by something derived from adjacency — which is a change to the identity model rather than to discovery, and it needs a requirement rather than an inference.

- **A VLAN read from the fallback table has no name, for ever.** `dot1qVlanCurrentTable` carries membership and no names, so a bridge that answers only it contributes a nameless membership. `VlanObservationApplier` never replaces a name with `null`, and `VlanAggregationRule` lets a nameless device abstain rather than vote — so one such switch beside five named ones costs nothing. An estate where *every* switch answers only the fallback gets a VLAN inventory of bare numbers, which is honest and not much use. CISCO-VTP-MIB and its equivalents are where the names are on those platforms, and reading one is a vendor-adapter change of the kind CDP was.

- **`dot1qPvid` is not read, so "which VLAN is this access port in" is inferred rather than answered.** The untagged member list is a good proxy — an untagged port is an access port, usually — but it is the VLAN's statement about the port rather than the port's about itself, and the two differ on a port configured in a VLAN whose static row an agent has not populated. One more column walk, and the natural home for it is whatever package first needs a port's VLAN rather than a VLAN's ports.

- **The VLAN walk is a third job per device, and the schedule still queues one at a time.** `TopologySchedulePass` refuses to queue a second `Discover` for a device that already has one outstanding, and now has three walks to get through — so a device due for everything takes three passes of `ScanIntervalSeconds` to be caught up, and at `SPEC.md` §1's 500 devices the estate's steady-state job rate went up by half without `MaxJobsPerScan` moving. Nothing is wrong at this scale; it is the sort of thing that stops being fine quietly, and the number to watch is queue depth rather than any of the intervals.

- **Nothing prunes a `device_vlans` row, and a withdrawn one is kept and read by nothing.** The same two gaps `device_neighbors` and `device_adjacencies` have, recorded again because the table is new: a VLAN removed from a switch keeps its row so that "VLAN 40 was on the core until Tuesday" stays answerable, and there is no endpoint that answers it and no retention policy that removes it. The volume is small — a VLAN per switch per reconfiguration — which is why it can wait for the retention package the other five tables are also waiting for.

- **Nothing draws the graph, and neither new walk has a button.** WP-2.4 owns the React Flow canvas and WP-2.3 the graph endpoint, so `GET /devices/{id}/adjacencies` and `/topology-scan` are reachable over the API and by nothing a person uses; and `POST /devices/{id}/neighbor-walk` and `/route-walk` join `client-walk` in having no trigger, so the only ways to read a device's topology are to wait fifteen minutes for the schedule or to send the request by hand. That is now three routes with the same gap on the same screen — the device detail's Fingerprint tab has the one walk button that exists — and they should be closed together rather than one at a time. It is the shape WP-1.9 closed for credential creation and it was found the same way, by walking the manual checklist.

- **A CDP-only neighbour on a port LLDP also speaks is suppressed, and it might be real.** `AdjacencyRule.Survivors` drops an account of a port whose *only* support is CDP when some other account of that port has LLDP behind it, which is the deterministic conflict resolution WP-2.1 was asked for. The case it gets wrong is a hub or a daisy chain where two things share one port and only one of them speaks LLDP: the second is a genuine neighbour and its edge is not drawn. Nothing is lost from the record — the observation is a live row on `device_neighbors` with a null `adjacency_id`, which is exactly the "why does it think that" evidence — but it is not in the edge set, so WP-2.3's graph and Phase 6's downstream suppression will not see it. A narrower rule would compare the two far ends rather than the two protocols, and it needs a real estate to know whether the case occurs often enough to be worth the complexity.

- **An edge is one row only if the far device has been fingerprinted.** Canonicalising two devices' accounts of one link onto one row needs the far end's `ifIndex`, which is resolved by matching the advertised port name against `device_interfaces` — and that table is populated by WP-1.5's fingerprint walk. A device promoted from discovery and never walked therefore produces two `Probable` edges for one cable rather than one `Confirmed` edge, both honest and neither wrong. In practice the topology schedule and the fingerprint schedule both run, so it self-corrects on the first walk of the far device; the failure is visible while an estate is still being brought up, which is exactly when somebody is most likely to be looking at it. `AdjacencyGraphTests.AFarEndWhosePortCannotBeResolved_StaysTheObservingDevicesOwnEdge` pins the behaviour so nobody later mistakes it for a bug.

- **Nothing prunes an observation, an edge or a topology-scan row.** The retention gap `collector_jobs`, `audit_log`, the delivered outbox rows, the discovery tables and the client tables already have, in its mildest form: an edge is bounded by ports rather than by time, so a stable estate's tables do not grow. What does grow is the withdrawn rows — a flapping link writes one withdrawn observation and one withdrawn edge per walk, every fifteen minutes, for as long as it flaps. They belong in the policy table Phase 8 builds, and the retention rule for them has to decide the same question the client tables raise: withdrawn rows are the record of what the estate *was*, which is the thing a topology history would read.

- **A withdrawn edge is kept and nothing reads one.** `device_adjacencies` and `device_neighbors` both carry `withdrawn_at` rather than being deleted, so "this link existed until Tuesday" is answerable from the database and from nowhere else — the adjacency route returns live edges only, and neither WP-2.3's graph nor WP-2.4's canvas is asked for history. That is the right default (a graph of every link that ever existed is not a topology) and it means the columns are currently write-only. The package that wants a topology timeline has the rows waiting for it.

- **An IPv6 next hop is usually link-local, and a link-local address matches no device.** The L3 half resolves a gateway by matching it against `devices.primary_ip_address`, and IPv6 routing tables overwhelmingly name a `fe80::/10` next hop, which is not routable and is therefore never a device's primary address. So an IPv6 remote route reliably produces a `Possible` edge to an unresolved far end. It is recorded honestly and it is close to useless; resolving it properly means reading the neighbour's link-local address per interface, which is `ipNetToPhysicalTable` — a table WP-1.8's client walk already reads for a different purpose. Worth revisiting in the package that first has an IPv6-routed estate to test against.

- **The two new walk routes are bounded per device and not in aggregate.** One outstanding `Discover` per device is refused with a `409` and `TopologyOptions.MaxJobsPerScan` bounds the schedule, and nothing stops a person holding `DiscoveryRun` asking for five hundred neighbour walks in five hundred requests. They join the same missing rate-limiting story as the unbounded on-demand walks, the unrate-limited discovery runs, the unrate-limited client walks and the unrate-limited sign-in — now five callers waiting on one package.

- **`TopologyResolver` reads every live device on every walk application.** Five hundred short rows once per applied walk, which at `SPEC.md` §1's target is nothing and is measurably simpler than the alternative: matching a management address against `primary_ip_address` in the database means comparing through `inet`, which EF cannot express without raw SQL — the same reason `ix_devices_primary_ip_address_live` is hand-written. It is documented at the query. If the estate ever outgrows the target this is the first thing to narrow, and the narrowing is a raw-SQL lookup rather than a redesign.

- **The client screen's "which port is it really on" can now be answered, and still is not.** WP-1.8 recorded that a MAC is learned by every bridge on the path to it, that the client list picks the port which learned the fewest addresses, and that WP-2.1's adjacency graph is what turns that evidence into an answer — an edge port is one with no neighbour on it. The graph now exists. Making the client list use it is a change to a WP-1.8 query and a WP-1.7 screen, which is why WP-2.1 did not make it; it is a small package and the first visible payoff of Phase 2 outside the topology screens.

- **`POST /devices/{id}/client-walk` has no button.** WP-1.5's fingerprint walk has one on the device's Fingerprint tab; WP-1.8 built the client walk beside it and gave it no trigger, so the only ways to read a device's client tables now are to wait up to fifteen minutes for the schedule or to send the request by hand. That is the same shape of gap WP-1.9 has just closed for credential creation — a route the API serves and the SPA cannot reach — and it was found the same way, by walking the manual checklist. The device screen is where it belongs, next to the walk button, and it is small: the mutation, a button and a toast.

- **The nullable-enum schema defect has now bitten twice, and the second time was pre-existing.** WP-1.8 recorded that a nullable enum member makes ASP.NET Core append `null` to the *shared* enum schema; WP-1.9 found that `SnmpAuthAlgorithm` and `SnmpPrivacyAlgorithm` have been generated as `| null` since WP-1.2, because `CreateCredentialProfileRequest` declares both as nullable. Every consumer of those enums reads as nullable although the API never sends one. WP-1.9 strips it at one boundary (`AuthAlgorithm` and `PrivacyAlgorithm` in `credentialLabels.ts`) rather than changing the contract, which is out of scope for a frontend package. The proper fix is the same schema transformer the `number | string` defect needs, and it now has two callers waiting for it.

- **A credential profile cannot be reached by name, only by list.** There is no `/devices/credentials/{id}` route: the screen is a list with dialogs over it, which is right at the scale a credential set has (dozens, not thousands) and means a profile cannot be linked to, bookmarked, or arrived at from an audit row naming it. The Administration screen in Phase 8 will want to link from an audit entry to the thing it acted on, and that is the point at which a detail route earns its place.

- **Nothing shows which devices a profile reaches.** The list says *how many* — `DeviceCount` is on the summary — and the removal confirmation says how many will lose it, but there is no way to see *which*. The API has no route for it either: `GET /devices/{deviceId}/credential-profiles` goes the other way. An operator about to rotate a credential for 40 devices would reasonably want the list, and it needs an endpoint before it needs a screen.

- **The rotation dialog opens an SNMPv3 profile at AES-128 rather than at the algorithm it holds.** `CredentialProfileSummary` carries no algorithm, so the dialog cannot know which privacy algorithm the profile was stored with, and it opens on a common default that the reader confirms. The server refuses a member that does not belong to the profile either way, so the failure mode is a refusal rather than a wrong write — but it is a guess shown to a person. Adding the algorithm to the summary is a one-member contract change and would remove the guess.

- **A nullable enum member on a response contract corrupts that enum for every other shape.** `AssetResolution` was written with a nullable `ClientObservationSource` — absent when no observation covered the instant — and ASP.NET Core's OpenAPI generator answered by appending `null` to the *shared* `ClientObservationSource` schema, so `ClientIpBindingSummary.source` and `ClientPortBindingSummary.source` started reading as `| null` in the generated TypeScript client although they never are. WP-1.8 avoided it by removing the member rather than working around it, because the source is diagnostic and lives on the binding summaries where it is always present — but the next package that wants a nullable enum on a response will hit the same thing and should know the shape of it before it does. It is the same family as the `number | string` defect below, and the same schema transformer would fix both.

- **Nothing prunes a client, a binding or a scan row.** The retention gap `collector_jobs`, `audit_log`, the delivered outbox rows and the discovery tables already have, with the largest shape yet: at `SPEC.md` §1's 5,000 clients, a guest VLAN on a short lease opens an address interval every time a device reconnects, and nothing ever removes one. Worse than the others in one way — `client_ip_bindings` is what every Phase 4 flow record and Phase 5 log event resolves through, so pruning it is deleting the evidence behind attributions already made, and a retention policy has to decide what a resolution answers once the interval it would have used has gone. It belongs in the policy table Phase 8 builds, and the client tables should be in the first list that policy covers.

- **An open binding can be arbitrarily old, and nothing says "this is stale".** WP-1.8 settled that an interval closes only when a conflicting observation supersedes it, because an ARP cache ages an entry out whether or not the host is still there — so a laptop that left the building a year ago still holds the last address anybody saw it on, and a resolution for last week answers with it. That is the honest record of what NetShield knows, and it is not what an operator means by "who is on 10.0.0.5". The screen shows `lastSeenAt` so a reader can see it; what does not exist is an idle window after which a binding is closed on the strength of having heard nothing. That is a policy guess rather than an observation and it belongs with the retention work, which will be looking at the same rows.

- **Which port a client is actually plugged into is not answered, only evidenced.** A MAC is learned by every bridge on the path to it, so a client has one open port binding on its access switch and one on every switch above it. All of them are true and all are recorded; the list picks the port that learned the fewest addresses, which is the evidence ordered by how much of it there is rather than a topology decision. WP-2.1's adjacency graph is what turns it into an answer — an edge port is one with no neighbour on it — and the client screen is the first place that will visibly improve when it lands. **The graph landed in WP-2.1 and nothing reads it yet**; see the note above.

- **Nothing reconciles a client that is also a device.** A router's own interface address appears in a neighbouring router's ARP cache, so it becomes a client row as well as a device row, and `AssetResolutionRule` prefers the device when both claim an address. What it does not do is *link* the two: the client row has no device reference, so the client list shows a switch's management MAC alongside the laptops with nothing saying it is one. Linking them means matching a MAC against `device_interfaces.physical_address`, which WP-1.5 already records — cheap, and out of scope for the package that noticed it.

- **Device resolution is current-address-only.** `devices` holds one address and no record of what it held before (WP-1.1), so `ResolveAssetAt` is time-accurate for clients and answers a device from the address it is reached on *now*, whatever the timestamp. The one case that is handled is a device created after the instant asked about, which falls back to the client observation — a discovery candidate promoted last Tuesday cannot have been the asset on Monday. What is not handled is a device that was *moved* between addresses: a flow from before the move resolves to it at the new address and not at the old one. Fixing it means a device address history, which changes the device update path and the API contract, and it is a package of its own. It is stated on `AssetResolution` so a caller can read it there rather than discovering it.

- **The warm-resolution assertion is on a percentile, not the median.** `AWarmResolutionAtTargetScale_IsUnderAMillisecond` asserts the tenth percentile of 200 warm resolutions at 5,000 clients. Measured on the machine this was written on: quiet, p10 356 µs and median 484 µs; with the rest of the integration suite running beside it, p10 432 µs and median 996 µs. The median crosses a 1 ms line under load and the percentile does not, so asserting the median would have shipped a second intermittently-failing test. The whole distribution is written to the test output either way. If the suite ever gets a way to run one class without the others beside it, the median is the better assertion.

- **A client walk is bounded per device and not in aggregate.** The same shape as the on-demand fingerprint walk and the discovery run route: one outstanding `Discover` per device is refused with a `409`, `ClientOptions.MaxJobsPerScan` bounds the schedule, and nothing stops a person holding `DiscoveryRun` asking for five hundred client walks in five hundred requests. It joins the same missing rate-limiting story as the unbounded on-demand walks, the unrate-limited discovery runs and the unrate-limited sign-in.

- **`clients.hostname` exists and nothing writes it.** SPEC.md §2 names a hostname in the client identity record, and the two sources that would supply one — a DHCP lease and a wireless association — are declared as `ClientObservationSource` members and deliberately unproduced. The column is there so the package that finds a real source writes a producer rather than a migration; until then the client list's hostname search matches nothing and the detail shows an em dash.

- **DHCP leases and wireless associations have no producer.** Confirmed at WP-1.8's scope gate rather than discovered: there is no source for either in V1 that does not mean inventing per-vendor MIB support the `SPEC.md` §4 vendor list does not cover. A DHCP server is not a network device NetShield reaches at all — the realistic source is its syslog, which is Phase 5's — and no platform in that vendor list is a wireless controller. Both are members of `ClientObservationSource` so that a binding can always say what its evidence was, and the package that finds a named, supportable source for either writes the producer.

- **The OUI is stored and no vendor name is resolved from it.** `clients.oui` holds the first three octets and the screen shows them as themselves, except for a locally administered address which is named as one — nobody registered it, so there is no vendor for a registry to name, and that is what address randomisation on a phone looks like. Turning a prefix into "Apple, Inc." needs the IEEE registry, whose licence, size and update cadence deserve a decision rather than a casual commit (confirmed at the scope gate). Whichever package takes it on should decide how the file gets into the repository and how it is updated, not just where it is parsed.

- **Nothing streams a client appearing or moving into the screen.** The same gap the device list has, now with a second screen behind it: `ClientDiscovered` is on the outbox, the client list reads once and stays as it is, and a laptop that plugs into a different port while somebody is looking does not move. `ARCHITECTURE.md` §9 gives the SPA one SignalR connection with per-route topic subscriptions; the package that stands it up owns both screens.

- **`ClientDiscovered` has no subscriber, and no event marks a handover.** The new-client event is published once per MAC, which is the shape Phase 6's "a new endpoint appeared on the network" rule would subscribe to. There is deliberately no event for an address changing hands, and that is the one a Phase 6 rule is more likely to want — "10.0.0.5 moved from that laptop to this one" is a security-interesting sentence. It was left out because nothing subscribes and inventing the payload before a subscriber exists is guessing at what it needs.

- **`ClientObservationApplier` relies on the outbox dispatcher being single-threaded.** It creates a client row for a MAC it did not find, with no upsert and no retry, which is correct only because WP-0.3 settled that exactly one process dispatches and it delivers one row at a time. The unique index on `mac_address` is what would catch it if that stopped being true — as a failed walk rather than a duplicate — and the note is here so that whoever ever makes the dispatcher concurrent knows this is one of the places to look.

- **A truncated client walk is recorded and not acted on.** `neighborsTruncated` and `forwardingTruncated` reach the log and nothing else. It costs nothing today because no binding is ever closed on the strength of an absence — so a partial reading is simply a smaller set of confirmations — but if an idle-expiry policy is ever written, that policy has to read these flags or it will close intervals on evidence a ceiling cut short.

- **The client walk reads two tables in one job and reports one outcome.** A device that answers its neighbour cache and then times out on its forwarding database fails the whole walk, so the ARP entries it did give are discarded. Failing is the safe direction, and it is the same trade WP-1.5 made for a subtree that fails partway through a fingerprint walk. A more forgiving version needs per-reading outcomes in the result payload, which is a contract change nobody has needed yet.

- **`useVirtualizer` opts three components out of the React Compiler**, up from two. `react-hooks/incompatible-library` now warns on `DeviceTable`, `DeviceInterfacesTab` and `ClientTable`: TanStack Virtual returns functions that cannot be safely memoized, so the compiler skips those components entirely. They are correct and fast at the target scale, and the warning matters only if a value from the virtualizer is ever passed into a memoized component elsewhere. These are the only warnings `npm run lint` emits.

- **The filters are parsed twice on a third screen, which is the third occurrence of one problem.** `validateSearch` gives the route its type and `parseClientFilters` runs again where the value is read, because a TanStack Router route inherits its parent's search parameters and merges its own over them. WP-0.7 hit it on the sign-in return path, WP-1.7 on the device filters, WP-1.8 on the client filters. The note WP-1.7 left said a third occurrence is the point at which a shared "validated search" helper is worth writing rather than each route remembering. This is that third occurrence.

- **The client list sorts by nothing a reader can change**, like the device list. It is ordered most-recently-seen first, which is the right default for "what is on the network", and the API offers no other order at all — so unlike the device list, the transport would have to grow before a header could be made clickable. Worth doing with the device list's sortable header rather than separately.

- ~~**The collector cannot lease a single job in the real stack.**~~ **Fixed, with the test gap that hid it.** `GET /internal/collector/jobs` answered 500 on every call: `LeaseCollectorJobsHandler` opened an explicit transaction for the `SELECT … FOR UPDATE SKIP LOCKED` claim WP-1.3 chose, and the composition root's `AddNpgsqlDbContext` configures a retrying execution strategy, which refuses a transaction it did not open — *"The configured execution strategy 'NpgsqlRetryingExecutionStrategy' does not support user-initiated transactions."* Every scheduled probe, walk and range sweep was dead in the running system while the suite stayed green. The claim now runs inside `context.Database.CreateExecutionStrategy().ExecuteAsync(...)`, which is how a retrying strategy and an explicit transaction are combined; because the delegate is re-run on a retry it clears the two result lists and the change tracker on entry, or a second attempt would report the first attempt's leases and try to save entities it had already mutated. **The reason no test caught it was that `InventoryHost` registered its contexts without `EnableRetryOnFailure` while the composition root registers them with it** — the test host was not wrong in the same ways production is. Found by running `aspire run` end to end for the first time, which was itself only possible once the DCP proxy regression below was worked around.

- **`Argon2idPasswordHasherTests.VerifyAsync_WithATamperedDigest_DoesNotMatch` fails about one run in sixteen, and always has.** It is WP-0.4's test and nothing in WP-1.7 touches it; it was caught because this package ran the suite often. The digest is 32 bytes base64-encoded and `TrimEnd('=')`-ed, so the final character carries two significant bits and four that decode to nothing. The test tampers by flipping that last character to `'A'` — or to `'B'` when it is already `'A'` — and `Convert.FromBase64String` ignores non-canonical trailing bits, so whenever the last character is one of `A`, `B`, `C` or `D` the "tampered" string decodes to the identical 32 bytes and the hash legitimately matches. That is 4 of 64 characters: **6.25%**, measured at 6.42% over 20,000 samples. The production code is correct — this is a defect in how the test constructs its tamper. Flipping a byte of the *digest* before encoding, or flipping a character in the middle of the field rather than at its end, both fix it in one line. **`main` is not reliably green until this is fixed**, and it belongs to whoever next touches the identity package.

- **Every number in the API contract is typed `number | string` in the generated client.** `ProblemDetails` also declares neither `code` nor `errors`, though every refusal carries a `code` (CONVENTIONS.md §4). Both come from how ASP.NET Core builds the OpenAPI document: `System.Text.Json` will *accept* a numeric string, so the generator writes `{"type": ["integer","string"]}` into the response schemas as well as the request ones. Nothing NetShield sends has ever been a numeric string. WP-1.7 is the first package to do arithmetic on an API number in the client and it felt it immediately — `totalCount === 1` was false for a single device, and `.toFixed` did not compile — so it coerces at one boundary (`src/lib/apiNumber.ts`) and reads a problem structurally. The proper fix is a schema transformer where the document is produced, which changes every numeric field for every consumer and belongs to a package that owns document generation rather than to the screen that noticed. Every use of `toNumber`, `requireNumber` and the structural problem read can be deleted the day it lands.

- **The outbox dispatcher logs a SQL query at `Information` once a second, for ever.** An idle `aspire run` wrote 5,000 lines in ten minutes, all of them the dispatcher's `SELECT ... FROM outbox_messages` poll at EF Core's `Microsoft.EntityFrameworkCore.Database.Command` category. CONVENTIONS.md §8 reserves `Information` for business events, and this buries every one of them — reading a real log line meant grepping past a thousand copies of the same query. Nothing is wrong with the dispatcher; the level EF logs commands at is what needs setting, in `appsettings.Development.json` or wherever the host configures logging. Noticed while diagnosing the `aspire run` health check, out of WP-1.7's scope.

- **The device table's row menu offers no destructive action.** DESIGN.md §6 gives every table row a trailing menu, and this one holds "Open device" and "Edit device". Removal lives on the device's own settings tab, where the typed confirmation can name the device the reader is actually looking at — a delete reachable from a row in a list of five hundred is a delete aimed by muscle memory. Worth revisiting if an operator asks for it, and the answer would still be a confirmation naming the device.

- **The device list sorts by nothing a reader can change.** The API offers six sort fields and `descending`, `DeviceListFilters` carries both, and the URL round-trips them — but no column header is clickable. It was left out because a sortable virtualized ARIA grid needs `aria-sort` on the header, a keyboard affordance and a decision about what a sort does to a cursor page, and none of that is named by the WP entry. The transport and the state are already there; it is a header component and a test.

- **Nothing streams a device state change into the screen.** The device list and detail read once and stay as they are until something invalidates them; a device that goes offline while somebody is looking at it does not move. `ARCHITECTURE.md` §9 gives the SPA one SignalR connection with per-route topic subscriptions, `DeviceStateChanged` is already on the outbox, and this is the first screen that would visibly benefit. The package that stands the connection up owns it.

- **A `site` filter matches one spelling of one site.** WP-1.1 recorded that `site` is free text rather than an entity; the filter is a text box for the same reason, and it matches exactly, ignoring case. Two operators spelling "HQ" and "Head office" produce two sites and neither filter finds the other's devices. Unchanged by this package and now visible on a screen, which is where somebody will notice it. A site aggregate is the fix and it needs a package of its own.

- **The discovery screen is reachable only from the device list.** There is no sidebar entry, because the sidebar is the reference screenshot's and DESIGN.md §9 admits no invented visual direction. A reader who does not know it exists will not find it. If a Discovery destination is ever wanted, that is a change to the reference rather than to the code, and it is the human's to make.

- **Seed create and edit are on the discovery screen, and SPEC.md §2 puts discovery schedules under Policies.** Built here at the human's instruction, because a fresh installation has no seed and a discovery screen that can run but cannot define a target is a dead end. The form covers name, description, ranges, exclusions, interval and enabled — everything the API accepts — and nothing else: maintenance windows, notification routing and the rest of the policy surface stay with the Policies package, which should decide whether to move these controls or link to them.

- **Nothing in the SPA tells a reader why a walk has not produced anything yet.** `POST /devices/{id}/walk` answers `202` with a job id and the screen says "Walk queued"; there is no job-status route to poll and no push, so the reader refreshes the fingerprint tab until it changes. A collector-job status endpoint would fix it and is a contract addition nobody has needed yet.

- ~~**Discovery has ten endpoints and no screen.**~~ **Answered in WP-1.7**: `/devices/discovery` has four tabs — candidate review defaulting to `status=New` with promote and ignore, run history, run detail with `addressCount` against `respondedCount` and the per-host list filtered by outcome, minimal seed CRUD, and the ignore list. - **Discovery has ten endpoints and no screen.** Seeds, runs, per-host outcomes, candidates, promotion, dismissal and the ignore list are all reachable over the API and none of them is reachable by a person. The review step SPEC.md §2 describes — "results appear as reviewable candidates" — is therefore only half built: the candidates exist and nobody can see them. WP-1.7's entry names "the discovery run view" and it is the package that closes this. It should expect to want a run's `addressCount` against its `respondedCount`, the per-host list filtered by outcome, and the candidate list defaulting to `status=New`.

So the review list shows `192.0.2.37` and nothing else — no hostname, no vendor, no reverse lookup — and an operator deciding whether to promote it has only the address and how many runs have seen it. Identifying a responder during the sweep would mean carrying several credentials on one lease, which is a collector-contract change; the cheaper half-step, if the review list turns out to be unusable, is one SNMP `sysDescr` read with a single named profile, which is one credential and no contract change. Worth revisiting after WP-1.7 has drawn the screen and somebody has used it.

It belongs in the policy table Phase 8 builds, and the discovery tables should be in the first list that policy covers.

- **A run cannot be cancelled, and a removed seed's run finishes anyway.** `collector_jobs` has no cancellation path — WP-1.3 settled that deliberately — so a sweep queued against a seed somebody then deletes is still leased, still run, and still applied to a run row that still exists. That is the honest behaviour for a historical record, but "stop this run" is a thing an operator will ask for the first time somebody points a seed at the wrong /16. It needs a cancellation state on the job contract, which is the seam WP-1.3 named.

- **The sweep's per-address timing is not adaptive.** Every address in a span gets the same one-second reply timeout and the same probe count, whatever the round trips on the range have looked like. `nmap` and its kin adapt; NetShield does not, so a slow WAN-attached range either takes a long time or under-reports, and the only knobs are estate-wide. Worth revisiting when the first range that is not a local VLAN is swept.

- **`MaxAddressesPerJob` and the collector's job timeout are not tied together.** A job of 256 addresses at 64 concurrent probes and a one-second timeout takes about four seconds; the collector abandons a job at `NETSHIELD_JOB_TIMEOUT_SECONDS`, which defaults to 120. Raising `MaxAddressesPerJob` to its 4,096 ceiling at the same concurrency would take about a minute — still inside the default, and outside a shorter one. Nothing checks the relationship; a unit test asserts only that the ceiling stays under what the collector will sweep at all.

- **An ignored candidate's last-seen does not move.** A sweep that finds an ignored address answering records the run's outcome and the count, and deliberately leaves the candidate row alone — so the review list's ordering is not disturbed by hosts nobody wants to hear about. The cost is that "this printer has answered every night for a year" is not visible on the candidate; it is derivable from the run host rows, which are what the retention policy above will eventually prune.

- **Seed CRUD publishes no event.** Devices, credential profiles and every discovery *run* announce themselves on the outbox; a seed changing does not, because nothing subscribes and a seed is configuration rather than an observation. If Phase 6's alerting ever wants "somebody widened the discovery scope", the audit row under `inventory.discovery-seed-update` is where it is visible today and an event is the change to make.

- **A discovery run is not rate limited across seeds.** One outstanding run per seed is enforced, which is the rule that matters, but a person holding `DiscoveryRun` can start a run of every seed at once and each fans out to `MaxJobsPerRun`. `MaxRunsPerScan` bounds the *schedule* and not the route. It is the same missing story as the unbounded on-demand walks and the unrate-limited sign-in, at a larger blast radius, and it belongs with whichever package writes the rate-limiting story.

- ~~**IPv6 discovery works and is not useful.**~~ **Half-answered in WP-1.8.** The neighbour-cache half is built: `ipNetToPhysicalTable` carries IPv4 and IPv6 in one walk and the collector reassembles a v6 address from the sixteen octets of its index, so an IPv6 host that has spoken to a router NetShield reads is now a client with an address, found without sweeping anything. - **IPv6 discovery works and is not useful.** `AddressRange` and the collector's sweep handle IPv6 exactly, and `MaxAddressesPerRun` refuses anything above 65,536 addresses — so a /112 sweeps and a /64 is refused at the endpoint. That is the correct refusal, and it means IPv6 discovery by sweep is only ever going to reach a hand-picked block. Finding IPv6 hosts properly needs neighbour-cache and DHCPv6 reads, which is WP-1.8's ARP/MAC/lease work rather than a sweep.

- **The collector opens one socket per address.** `collector.discovery.sweep` calls `collector.icmp.probe.probe` once per address, and each call opens, uses and closes its own ICMP socket. At 64 concurrent that is 64 open at a time and 256 opened per job, which is fine at this scale and is wasteful at a larger one. A sweep that shared one socket across a span would be faster and would mean moving the socket out of `probe`, which is WP-1.4's shape and not worth disturbing until a real range is slow.

- **The session query is nullable below the guard, and one component leans on it.** `_app` resolves the session before the shell renders, so there is always one — except in the frame between signing out and the redirect landing, when the cache is empty and the shell is still mounted. `useSession` returns `undefined` there, `usePermissions` holds nothing, and `UserBlock` draws nothing. A future component below the guard has to tolerate the same gap; a hook that promised a user would have to suspend with no boundary above it or assert past the gap, and both turn a one-frame absence into a render loop.
- **Nothing hides a route from the router, only from the sidebar.** There is no per-route permission declaration and no 403 screen. If a later package wants a screen to refuse before it renders, `_app`'s `beforeLoad` is where that goes, and it needs a designed "you cannot see this" state — which `DESIGN.md` does not have.
- **The reference dashboard's content is not built.** WP-0.6 built the chrome — sidebar, header, routing, theme — and every route renders a placeholder. The KPI strip, topology canvas, bandwidth chart, security donut, recent-alerts table, top-applications donut and device-health list in `docs/design/reference-dashboard.png` are the dashboard work in Phase 8, and Recharts, React Flow and `dagre` are deliberately not installed yet.
- **The notification bell shows no count.** `NotificationBell` takes one and renders the badge when it is above zero; nothing counts anything until the alerting work in Phase 6. The reference screenshot shows `12`, and inventing a number to match it would have been worse than the gap.
- **`Security ›` has invented children.** The screenshot shows the chevron but not what is behind it, and `SPEC.md` §2 has no Security area of its own. `/security/posture` and `/security/findings` are placeholders chosen so the section is not a chevron over nothing; whichever Phase 7 package builds the posture surface should rename them. Reports and Administration children come straight from `SPEC.md` §2 and need no such warning.
- **Light mode is derived, not designed.** `DESIGN.md` §2 makes the toggle V1 scope and says light is derived from the dark tokens. `theme.css` derives it by moving only the surface and text roles and leaving every semantic hue alone. It has never been looked at against a reference, because there is no light reference. The `[data-theme='light']` block is the only place in the SPA holding a colour `DESIGN.md` §3 does not name, and the token test exempts it for exactly that reason.
- **No SignalR.** `ARCHITECTURE.md` §9 gives the SPA one connection with per-route topic subscriptions. Nothing publishes yet, so nothing subscribes; the package that first has a live stream to push owns standing the connection up.
- **The SPA build writes into `src/NetShield.Web.Host/wwwroot`, which is git-ignored.** That is deliberate — nothing copies the build, so nothing can copy a stale one — but it means `dotnet publish` on its own produces a host with no SPA in it. The package that writes `docker-compose.yml` has to run `npm run build --prefix src/NetShield.Web.Client` before publishing the host, or add an MSBuild target that does.
- **Regenerating the API contract is a two-step manual flow.** Change an endpoint, run the suite once with `NETSHIELD_UPDATE_OPENAPI=1` to rewrite `openapi/v1.json`, then `npm run api:generate --prefix src/NetShield.Web.Client` to rewrite `schema.d.ts`, then commit both. Two tests fail until you do, which is the point, but a single `regen` script would be kinder and belongs with whoever next changes the contract.
- **The OpenAPI document is produced by a test host, not by the composition root.** `ARCHITECTURE.md` §4 lets nothing reference `NetShield.Web.Host`, and build-time document generation would run `Program.cs` without the Aspire connection strings it demands. `ApiDocumentParityTests` fails if `Program.cs` maps an endpoint group the document host does not, which closes the obvious hole; the cost is that a second file has to gain a line whenever a module's endpoints are first mapped.
- **`MapNetShieldSpa` lives in `NetShield.Platform`, not in `Web.Host`.** Same reason: "the shell is reachable without a session" is worth an integration test and nothing may reference the composition root. `ARCHITECTURE.md` §4 describes Platform as cross-cutting and does not list SPA hosting; if that reads as a stretch, the alternative is to leave the claim untested.
- **A resource name with a hyphen cannot reach a process npm starts.** Aspire names a service-discovery variable after the resource, so `web-host` produces `services__web-host__http__0` — and `npm run dev` runs its script through `sh -c`, where a POSIX shell exports only names that are valid shell identifiers. The variable is silently dropped between `sh` and `node`. The AppHost therefore also passes `NETSHIELD_API_URL`, and `OrchestrationTests` fails if that goes missing or if the resource is ever renamed to something a shell would have carried. Any future resource started through a shell has the same trap; Aspire's own `WEB_HOST_HTTP` (uppercased from the resource name) is an alternative, but it changes silently when the resource is renamed. Running the SPA without `aspire run` still needs `NETSHIELD_API_URL` set by hand.
- **Two npm packages are pinned below their latest major.** `typescript` is held at 5.9 because `typescript-eslint` 8 does not accept 6.x yet. Worth revisiting when it does.
- **The 1536px layout has not been checked in a browser by the agent.** There is no headless browser on this machine — Playwright's Chromium needs system libraries that require `sudo` to install — so "matches the reference at 1536px" is on the manual checklist rather than in a test. A visual-regression check is worth a package of its own once the dashboard content exists to regress.
- **There is no user administration.** Nothing creates, disables, renames or resets a second account — the seeded administrator is the only account the system can produce. Whichever package owns the Administration screen in Phase 8 needs user CRUD, an administrator-initiated password reset that sets `must_change_password`, and a way back in when the sole administrator is locked out.
- **Sign-in is not rate limited.** Lockout bounds attempts against one account; nothing bounds attempts across many accounts from one source, and nothing spends Redis on it yet. Worth a look when the rate-limiting story is written, since the Argon2id verification on every attempt is itself the expensive part.
- No authentication event reaches the outbox. WP-0.5 records sign-in, lockout and password change in `audit_log`, which is the human-facing record; `UserSignedIn`, `AccountLockedOut` and `PasswordChanged` as integration events are still unbuilt, and are what a notification rule in Phase 6 would subscribe to. The audit row is not a substitute — nothing subscribes to a table.
- `Identity:Seed:Password` reaches `Web.Host` as an environment variable from an Aspire parameter persisted to the AppHost's user secrets. Deployment has no equivalent yet; the package that writes `docker-compose.yml` has to decide how a mounted secret gets there, and the same question covers the credential KEK in WP-1.2.
- The Argon2id work factor is a single global setting. Raising it rehashes each account on its next sign-in and never on its own, so an account that has not signed in since a change keeps the older cost until it does.
- **The lab is still not stood up, and WP-1.5, WP-1.8, WP-2.1 and WP-2.2 have all now shipped without it.** *(WP-2.2 added five more under `src/netshield-collector/tests/fixtures/snmp/vlans/`, on the same terms. One of them exists because of a hazard nobody would have predicted from the documentation: a `PortList` is a bitmap and `session.decode` cannot know that, so the same kind of value is recorded as `00:30` on one switch and as `` ` `` on the next. A real recording would have found that; hand-authoring it meant reasoning it out from `decode` instead, which is exactly the sort of thing a real corpus is for.)* *(WP-2.1 added nine hand-authored fixtures under `src/netshield-collector/tests/fixtures/snmp/topology/`, at the human's instruction and on the same terms: the format is the contract, so a real `snmpsim` recording replaces a file without changing a test. They are the biggest bet on that terms so far — LLDP's local-port join and CDP's raw-octet address column are exactly the places a real agent differs from its documentation, and the three fixture switches each exercise a different one of the three port-resolution routes precisely because nobody has seen a real one. The original WP-1.5 note follows and is unchanged.)* The seven walk fixtures under `src/netshield-collector/tests/fixtures/snmp/` are hand-authored from documented `sysObjectID` arcs and `sysDescr` formats, clearly marked synthetic, and they prove exactly what they can prove: that the resolver reads those two fields correctly and that each adapter extracts the three facts from the right place. What they cannot prove is that a real agent's `sysDescr` matches the format its vendor documents, that a real `entPhysicalTable` puts the chassis where expected, or that a private OID is answered at all. Containerlab plus an `snmpsim` corpus (see `WORKFLOW.md` § Test data) is what closes that, and replacing a fixture file with a real recording of the same platform should change nothing but realism — the format is the contract. Worth doing before Phase 2's neighbour collection, which reads far more vendor-variable tables than this package does.
- `docker-compose.yml` is in the `CONVENTIONS.md` §1 layout and `ARCHITECTURE.md` §2 names Docker Compose as the deployment orchestrator, but no Phase 0 package creates it. It needs a package of its own, most naturally in Phase 8 alongside hardening.
- **`dotnet test` now needs a Docker daemon** for `NetShield.IntegrationTests` alone. WP-0.3 gave that project its first tests and the Testcontainers dependency `CONVENTIONS.md` §7 requires; unit and architecture tests stay container-free, so a layer can still be run on its own. The WP-0.2 "Done when" criteria — dashboard health, `/health`, `/health/ready`, and the `timescaledb` extension version — are still verified by hand rather than by a test, and the harness to automate them now exists.
- `WORK_PACKAGES.md` WP-0.2 names **MailHog**; the build uses **MailPit** (`axllent/mailpit:v1.31.0`) instead. MailHog was archived upstream in 2024 at v1.0.1. MailPit is the maintained drop-in with the same SMTP-sink and web-UI role, and it ships a `/readyz` endpoint that lets the dashboard report the resource healthy. The WP text has not been edited; this note is the record of the deviation.
- `ServiceDefaults.MapDefaultEndpoints` maps the health endpoints in the Development environment only, which is the Aspire template's default and the reason a `dotnet run` outside Aspire answers 404 there. A Docker Compose deployment will need container health checks against these paths, so the package that writes `docker-compose.yml` has to decide deliberately whether to expose them in production and on which interface.
- `NetShield.UnitTests` reaches the Postgres container's resolved environment through `GetEnvironmentVariableValuesAsync`, which Aspire 13.5.3 marks obsolete; its replacement, `ExecutionConfigurationBuilder`, is not public in that version. The call is behind a scoped `#pragma` in `AppHostModel`. Revisit when Aspire makes the replacement public.
- The AppHost pins `timescale/timescaledb:2.29.0-pg17` and `axllent/mailpit:v1.31.0` by literal; Redis floats on the Aspire default (8.6 today). Container image versions have no equivalent of `Directory.Packages.props` and nothing yet updates them.
- The `ARCHITECTURE.md` §4 module rules are enforced over the **project-reference graph**, not over loaded assemblies, because a reference an empty project declares is elided from assembly metadata and a reflection rule would pass over all ten modules vacuously. Two §4 rules are therefore still unenforced and need an assembly-level rule library (NetArchTest or ArchUnitNET) in WP-1.1, once a module holds real types: *cross-module communication carries `Contracts` types only*, and *no module exposes an EF entity across its boundary*.
- **Migrations are applied by `NetShield.Web.Host --migrate`, not on startup** (settled in WP-1.1). The same artifact, run with an argument, applies `PlatformDbContext`, `IdentityDbContext` and `InventoryDbContext` in that order — Platform first, because it owns `outbox_messages`, which the Inventory context maps and excludes from its own migrations — then starts the host just long enough for the first-run seeder to run, then exits. It is a generic host and binds no socket. The AppHost runs it as the `db-migrator` resource and `web-host` `WaitForCompletion`s it, so `aspire run` on an empty volume comes up migrated and with an administrator. It is idempotent: a second run reports each context up to date and seeds nothing. **Deployment still has no equivalent** — the package that writes `docker-compose.yml` has to run the same image with the same argument as a one-shot service before the API starts, and decide how the least-privilege DDL credential differs from the API's.
- `IntegrationEventRegistry` keys an outbox row by the event type's `FullName`, so moving or renaming an event type is a breaking change for rows still in flight. Fine while nothing is deployed; revisit before the first release if event types look likely to move.
- The outbox dispatcher assumes it is the only one running — it claims rows with a plain query rather than `FOR UPDATE SKIP LOCKED`. Correct for the single-node V1 in `SPEC.md` §3, and the reason `AddOutboxDispatcher` is a separate opt-in call that only `Web.Host` makes. A second dispatching process would double-deliver.
- Delivered outbox rows are kept, and nothing prunes them. They belong in the retention policy table `ARCHITECTURE.md` §3 describes, which arrives with the policy work in Phase 8.
- `OutboxPayload` uses reflection-based `System.Text.Json` rather than a source-generated context. `CONVENTIONS.md` §4 requires source generation for the API's JSON; these rows are internal and never leave the process, but the choice would have to be revisited if a NetShield process were ever published trimmed or AOT.
- `.editorconfig` carries placeholder sections for `*.py` and `*.{ts,tsx,...}` ahead of the collector (WP-1.3) and the SPA (WP-0.6). Revisit them when those toolchains land — `ruff` and Prettier own formatting there, not `dotnet format`.
- `Directory.Packages.props` now sets `CentralPackageTransitivePinningEnabled`, which surfaced two existing transitive downgrades and moved `Microsoft.Extensions.Hosting` from 10.0.0 to 10.0.11 to clear them. Every EF Core package is pinned at 10.0.11 and the local `dotnet-ef` tool was updated to match; a future `aspire update` has to keep the two in step.
- **The audit row is written after the domain change commits, not with it.** The middleware records once the endpoint has answered, in its own transaction, which is what lets it record a 401 or a 403 the endpoint never saw. A process death in the window between the two loses the row. Accepted deliberately (see `DECISIONS.md`); if audit ever has to be atomic with the change it describes, the answer is to route it through the transactional outbox, not to hand-write an append into every handler.
- **`source_ip` is the socket's remote address, with no forwarded-headers handling.** Behind a reverse proxy — which is how a Docker Compose deployment will run — every audit row would name the proxy rather than the user. The package that writes `docker-compose.yml` has to configure `UseForwardedHeaders` with a trusted-proxy list, and it must be a list rather than "trust everything", or the field becomes attacker-controlled.
- **Deny-by-default now applies to every endpoint added from here on.** An endpoint with no policy answers 401. WP-0.6's SPA hosting is the first thing this will bite: `MapFallbackToFile` and the static-file routes have to declare `AllowAnonymous()`, or the sign-in page itself will require a session.
- **Nothing reads the audit log.** `Permission.AuditRead` is defined, granted to the Administrator, and unused — there is no query endpoint and no screen. The Administration screen in Phase 8 owns both, and will need cursor pagination and filters by actor, action, target and time.
- **Nothing prunes `audit_log`.** Like the delivered outbox rows, these belong in the retention policy table `ARCHITECTURE.md` §3 describes. Unlike the outbox rows, pruning them is a policy decision with a compliance edge to it, and the database rule refuses a `DELETE` — whatever prunes it will have to drop the trigger, delete, and restore it, deliberately and audibly.
- **The `must_change_password` claim can go stale in one direction.** It is minted at sign-in and re-minted on refresh and on the change that clears it. An administrator setting the flag on somebody else's account mid-session would not refuse that session until it refreshes. Nothing can set it today; whichever package adds administrator-initiated password reset has to decide whether a forced reset also revokes the target's sessions.
- **The permission set is defined but barely exercised.** Only the test project's probe endpoints call `RequirePermission`, because no module endpoint exists yet. Every package from WP-1.1 on has to declare a permission per endpoint, and the first few will show whether the grain is right — it is much cheaper to split a permission now than after a dozen endpoints name it.
- `AuditPayload` serialises before/after with reflection-based `System.Text.Json`, the same choice and the same caveat as `OutboxPayload`: internal, never leaves the process, would have to be revisited if a NetShield process were ever published trimmed or AOT.
- The audit snapshot member names avoid the words `SecretRedactor` treats as secret — `changeRequired` rather than `mustChangePassword`. It works and it is documented at both call sites, but it is a trap for the next author, who will name a field honestly and find `[REDACTED]` in the column. Worth a lint or a test that fails when a snapshot key is one the redactor would blank.

- **The module-level `IResourceGuard` check is never the one that refuses, in practice.** Every device handler calls it, but the endpoint's `RequirePermission` has already refused the same caller, so the second check is dead weight on every request that reaches a handler. That is deliberate — ARCHITECTURE.md §8 wants it there for the batch operation or background job that has no endpoint in front of it — but it means no integration test can prove the module check works on its own, and `ResourceGuardTests` in the unit suite is the only thing that does. The first handler reached from something other than a route is what will prove it in anger.
- **`DeviceUpdated` fires even when nothing changed.** A PUT that sets every member to the value it already held still writes an outbox row and an audit row. Detecting a no-op would mean comparing the snapshot before and after, which is cheap — but "nothing changed" is a judgement about which fields count, and no subscriber exists yet to have an opinion. Worth revisiting when one does.
- **The device list counts every match on every page.** `totalCount` costs a second query per request. Cheap at 500 devices; the first thing to drop if the estate grows past what `SPEC.md` §1 designs for, and `CursorPage.TotalCount` is optional by design so nothing breaks when it goes.
- **Nothing bounds how many devices exist.** `SPEC.md` §1 targets 500 and nothing enforces it. A create loop would fill the table, and the audit and outbox rows with it. Whatever adds rate limiting to sign-in should look at the write endpoints too.
- **`site` and `owner` are free text, not entities.** `SPEC.md` §2 names sites in the inventory read permission, and WP-1.7 wants to filter by site — which works today only because the filter matches the string exactly, ignoring case. Two operators spelling one site differently produce two sites. A site aggregate is the fix, and it needs a package of its own; until then, the filter is as good as the typing.
- **The `inet` column's containment operators are unused.** `primary_ip_address` is `inet`, so `<<` against a CIDR is available and would be the natural way for WP-1.6 to ask "is this discovered host already a device". Nothing uses it yet, and EF cannot express it without raw SQL — the same reason its unique index is raw SQL.
- **The `Inventory_AddDevices` migration carries hand-written SQL.** The unique partial index on `primary_ip_address` is a `migrationBuilder.Sql` call, because EF refuses to index a property whose CLR type is not `IComparable` and `IPAddress` is not. It is therefore absent from `InventoryDbContextModelSnapshot`, so a later `dotnet ef migrations add` will neither drop it nor recreate it — which is what we want, but it does mean the model snapshot is not the whole schema for this table. Any later change to that index has to be written the same way.
- **`db-migrator` and `web-host` are the same project twice in the AppHost.** Aspire builds it once and runs it twice, which is the point, but the dashboard shows two resources with one source and a reader could mistake the migrator for a second API. It exits immediately, which is the tell.
