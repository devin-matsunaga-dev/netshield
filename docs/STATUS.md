- **WP-1.4 — ICMP reachability and device state** (2026-09-04, `feat/wp-1.4-icmp-reachability`). **The collector queue has a producer and `CollectorJobCompleted` has a subscriber** — the two seams WP-1.3 shipped empty are now closed by the same package that fills them. `collector/icmp/` is three layers with nothing shared between them: `packet.py` is RFC 792 and RFC 4443 as functions from bytes to bytes (checksum, echo request, reply parsing, IPv4 header stripping) and opens no socket; `probe.py` opens one and times what comes back; `executor.py` is the first `JobExecutor` and answers for `Poll` jobs whose parameters name the ICMP probe. **No new dependency and no change to the WP-1.3 wire contract**: no `CollectorJobKind` member, no field on the lease, result or heartbeat. What WP-1.4 fills in is the `parameters`/`data` documents WP-1.3 deliberately left opaque, discriminated by a `probe` member so that a Phase 3 SNMP `Poll` row and a Phase 1 ICMP `Poll` row can tell each other apart in one table. The socket is `SOCK_DGRAM`/`IPPROTO_ICMP` first and `SOCK_RAW` second, and if neither opens the job **fails** naming `ping_group_range` and `CAP_NET_RAW` rather than reporting loss. **A collector failure is never evidence about a device**: a probe that ran and heard nothing is a *successful* job at 100% loss, while a probe that could not be performed is a *failed* job recorded on the reachability row's `last_error` with the device's state and its run of observations untouched — otherwise one process losing a capability would take five hundred devices offline and the alert would name the wrong thing. `device_reachability` (migration `Inventory_AddDeviceReachability`) is a table of its own rather than columns on `devices`, because a counter that changes every sixty seconds has no business touching the row the device list sorts by `updated_at`; `devices.state` stays the published state and is written only on a transition, and a transition deliberately does not stamp `devices.updated_at`. The state machine is one pure function: classify a probe as Online (no loss), Warning (some) or Offline (all), then adopt it only after `SuccessThreshold`/`FailureThreshold` consecutive identical observations — which is why a flapping device emits **no** transition at all rather than one per probe, and why a week-long outage is one `DeviceStateChanged` and not ten thousand. The result handler is idempotent by `last_applied_job_id`, because outbox delivery is at-least-once and a redelivered probe would otherwise advance a run halfway to a threshold only one probe supports. `ReachabilitySchedulePass` queues one probe per due device and stamps the next due time in one transaction through the new enlisting form of `ICollectorJobQueue` — the gap WP-1.3 left for "the first package that actually needs it" — skips any device with a probe still outstanding so a collector outage cannot build a backlog nobody will run, and spreads the next due time by a device-derived offset under one scan so an estate imported in one go does not fall due in one second for ever. `ReachabilityScheduler` is opt-in from the composition root for the reason `AddOutboxDispatcher` is: exactly one process schedules the estate, and the schema step registers the same module. 919 tests: 722 backend (425 unit, 256 integration, 41 architecture), 123 frontend, 74 collector.

- **WP-1.2 — Credential profiles and envelope encryption** (2026-09-04, `feat/wp-1.2-credential-profiles`). Envelope encryption lives in `NetShield.Platform.Cryptography`, where `ARCHITECTURE.md` §4 puts crypto: `AesGcmEnvelopeEncryptor` generates a fresh 256-bit data-encryption key for every value, seals the value under it with AES-256-GCM, and seals the key under the ring's active key-encryption key. The `context` string — `credential-profile:{id}` — is bound in as additional authenticated data at both layers, so a blob copied into another row's columns fails to open rather than yielding the wrong device's credential. `KeyEncryptionKeyRing` decodes the configured keys once and `EnvelopeEncryptionOptionsValidator` fails the host at startup: **a key is 32 random bytes, base64-encoded, and nothing else** — not a pass phrase, not something a KDF is run over, because no derivation adds entropy an input never had and a KEK must be at least as strong as the keys it wraps. `NetShield.Inventory` holds `credential_profiles` and `device_credential_profiles` (migration `Inventory_AddCredentialProfiles`). Four kinds — SNMP v2c community, SNMP v3 auth/priv, SSH password, SSH key — with every secret member for the kind in one sealed `bytea` rather than a column per secret; `CredentialMaterialPayload` is its own type with explicit JSON names, so renaming the wire contract cannot silently break bytes already at rest. `name` is unique among live rows, case-insensitively, and a soft delete releases it. Six endpoints under `/api/v1/credential-profiles` plus `GET`/`PUT /api/v1/devices/{deviceId}/credential-profiles`, **every one of them behind `CredentialsManage`, reads included** — there is no `CredentialsRead` member and a profile's username is half of an SSH credential. The material has a route of its own, `PUT /{id}/material`, because a secret that is never returned cannot be round-tripped through a whole-resource PUT. Which members a kind requires is a semantic rule answering 422 (`CredentialKindRules`), and both directions are checked: a missing member is refused and so is one belonging to another kind. The decrypt path is `ICredentialResolver`, **internal to the module, with no HTTP surface in this package** — WP-1.3 owns the collector-job endpoint it will be reached from. Key rotation is `NetShield.Web.Host --rewrap`, not a route: it re-wraps each profile's data key under the active KEK without ever reconstructing a plaintext or rewriting a payload column, covers soft-deleted rows so a retired key can actually be dropped, is safe to repeat, and writes its own `audit_log` row rather than being put on the web attack surface to inherit the middleware's. Four events — `CredentialProfileCreated`, `CredentialProfileUpdated` (carrying `MaterialChanged`), `CredentialProfileRemoved`, `DeviceCredentialProfilesChanged` — carry ids and a kind and nothing else. `ApiSecretExposureTests` walks every response schema in the committed OpenAPI document and fails the build if a member appears that `SecretRedactor` would blank, so the guarantee holds for every package after this one and not just this one. 699 tests: 576 backend (345 unit, 200 integration, 31 architecture) and 123 frontend.

- **WP-1.3 — Collector service skeleton and job contract** (2026-09-04, `feat/wp-1.3-collector-skeleton`). The internal contract from `ARCHITECTURE.md` §7 — `GET /internal/collector/jobs`, `POST /internal/collector/results`, `POST /internal/collector/heartbeat` — served by `NetShield.Inventory` and mapped from `MapInventoryEndpoints`. They are **outside `/api` on purpose**: the OpenAPI document filters on that prefix and the TypeScript client is generated from it, so a lease response carrying an opened device credential can never enter a browser's contract, and an architecture test fails the build if an `/internal` path ever appears there. Authentication is a bearer scheme in `NetShield.Platform.Authentication`, registered from `AddNetShieldInventory` the way WP-1.2's key ring is, comparing SHA-256 digests in fixed time so neither the secret nor its length leaks; its policy names the scheme, so **a signed-in administrator cannot open the internal contract and a collector cannot open `/api`** — the two credentials open disjoint sets of routes. `collector_jobs` and `collectors` (migration `Inventory_AddCollectorJobs`) hold the queue and the fleet's liveness. A claim is `SELECT … FOR UPDATE SKIP LOCKED` inside a transaction — the one table in NetShield more than one process really competes for — and each claimed job gets a lease token of its own, so a result is accepted only under the generation currently on the row: a retry is a no-op, and a collector whose lease expired cannot overwrite the result of whoever holds it now. ## In flight / noticed

Things spotted during a package that are out of its scope. Do not fix them in the current package — record them here and address them in a package of their own.

- **Discovery has ten endpoints and no screen.** Seeds, runs, per-host outcomes, candidates, promotion, dismissal and the ignore list are all reachable over the API and none of them is reachable by a person. The review step SPEC.md §2 describes — "results appear as reviewable candidates" — is therefore only half built: the candidates exist and nobody can see them. WP-1.7's entry names "the discovery run view" and it is the package that closes this. It should expect to want a run's `addressCount` against its `respondedCount`, the per-host list filtered by outcome, and the candidate list defaulting to `status=New`.

- **A candidate is a bare address, and stays one until it is promoted.** The sweep asks one question and identification is WP-1.5's walk, which runs against devices. So the review list shows `192.0.2.37` and nothing else — no hostname, no vendor, no reverse lookup — and an operator deciding whether to promote it has only the address and how many runs have seen it. Identifying a responder during the sweep would mean carrying several credentials on one lease, which is a collector-contract change; the cheaper half-step, if the review list turns out to be unusable, is one SNMP `sysDescr` read with a single named profile, which is one credential and no contract change. Worth revisiting after WP-1.7 has drawn the screen and somebody has used it.

- **Nothing prunes a discovery run, its host rows, or its candidates.** The same retention gap `collector_jobs`, `audit_log` and the delivered outbox rows already have, with a new shape: a nightly sweep of a /22 that finds 400 hosts writes 400 host rows a night for ever, and a candidate that was dismissed stays for ever by design. It belongs in the policy table Phase 8 builds, and the discovery tables should be in the first list that policy covers.

- **A run cannot be cancelled, and a removed seed's run finishes anyway.** `collector_jobs` has no cancellation path — WP-1.3 settled that deliberately — so a sweep queued against a seed somebody then deletes is still leased, still run, and still applied to a run row that still exists. That is the honest behaviour for a historical record, but "stop this run" is a thing an operator will ask for the first time somebody points a seed at the wrong /16. It needs a cancellation state on the job contract, which is the seam WP-1.3 named.

- **The sweep's per-address timing is not adaptive.** Every address in a span gets the same one-second reply timeout and the same probe count, whatever the round trips on the range have looked like. `nmap` and its kin adapt; NetShield does not, so a slow WAN-attached range either takes a long time or under-reports, and the only knobs are estate-wide. Worth revisiting when the first range that is not a local VLAN is swept.

- **`MaxAddressesPerJob` and the collector's job timeout are not tied together.** A job of 256 addresses at 64 concurrent probes and a one-second timeout takes about four seconds; the collector abandons a job at `NETSHIELD_JOB_TIMEOUT_SECONDS`, which defaults to 120. Raising `MaxAddressesPerJob` to its 4,096 ceiling at the same concurrency would take about a minute — still inside the default, and outside a shorter one. Nothing checks the relationship; a unit test asserts only that the ceiling stays under what the collector will sweep at all.

- **An ignored candidate's last-seen does not move.** A sweep that finds an ignored address answering records the run's outcome and the count, and deliberately leaves the candidate row alone — so the review list's ordering is not disturbed by hosts nobody wants to hear about. The cost is that "this printer has answered every night for a year" is not visible on the candidate; it is derivable from the run host rows, which are what the retention policy above will eventually prune.

- **Seed CRUD publishes no event.** Devices, credential profiles and every discovery *run* announce themselves on the outbox; a seed changing does not, because nothing subscribes and a seed is configuration rather than an observation. If Phase 6's alerting ever wants "somebody widened the discovery scope", the audit row under `inventory.discovery-seed-update` is where it is visible today and an event is the change to make.

- **A discovery run is not rate limited across seeds.** One outstanding run per seed is enforced, which is the rule that matters, but a person holding `DiscoveryRun` can start a run of every seed at once and each fans out to `MaxJobsPerRun`. `MaxRunsPerScan` bounds the *schedule* and not the route. It is the same missing story as the unbounded on-demand walks and the unrate-limited sign-in, at a larger blast radius, and it belongs with whichever package writes the rate-limiting story.

- **IPv6 discovery works and is not useful.** `AddressRange` and the collector's sweep handle IPv6 exactly, and `MaxAddressesPerRun` refuses anything above 65,536 addresses — so a /112 sweeps and a /64 is refused at the endpoint. That is the correct refusal, and it means IPv6 discovery by sweep is only ever going to reach a hand-picked block. Finding IPv6 hosts properly needs neighbour-cache and DHCPv6 reads, which is WP-1.8's ARP/MAC/lease work rather than a sweep.

- **The collector opens one socket per address.** `collector.discovery.sweep` calls `collector.icmp.probe.probe` once per address, and each call opens, uses and closes its own ICMP socket. At 64 concurrent that is 64 open at a time and 256 opened per job, which is fine at this scale and is wasteful at a larger one. A sweep that shared one socket across a span would be faster and would mean moving the socket out of `probe`, which is WP-1.4's shape and not worth disturbing until a real range is slow.


- **Nothing exposes a fingerprint or an interface inventory over the API.** The four identity facts land on `devices` and so appear on `DeviceDetail` already, but everything else the walk established is reachable only from the database: `sysObjectID`, `sysDescr`, `sysName`, uptime, when the device was last walked, `last_error` when it could not be, `overridden_fields`, and the whole of `device_interfaces`. WP-1.7's device screen is what needs them, and it needs `reduced_capability` in particular — SPEC.md §4 requires a generic-SNMP device's reduced feature set to be *clearly labelled in the UI*, and WP-1.5 has made that a recorded fact without giving anything a way to read it. This is the same shape as the reachability-detail gap below, and the two should be answered by one package.

- **The override rule is derived, not declared, and it can be fooled.** A walk owns the four identity facts unless the device's current value differs from what the *previous* walk discovered, which is how "operator override" is answered without a provenance column WP-1.1 never had and WP-1.5 was not told to add. It is right in the ordinary cases and wrong in one: an operator who edits a field and then sets it back to the discovered value has their intent forgotten, and one who edits a field that no walk has ever discovered is not recorded as having overridden anything. The clean model is a per-field provenance marker written at the point of edit, which means touching the device update path and the API contract. `device_fingerprints.overridden_fields` is where the current answer is visible; WP-1.7, which has to render the distinction, is the natural place to decide whether it is worth declaring properly.

- **Six vendor adapters claim `ConfigFetch` and nothing can serve it.** `supported_kinds` is a statement about what the *vendor* supports, which is what makes generic SNMP's reduced feature set expressible at all — it is the only adapter without `ConfigFetch`. But no `ConfigFetch` executor exists, so the claim is unexercised until Phase 7 builds SSH retrieval. If Phase 7 finds a vendor whose CLI NetShield cannot actually drive, the honest fix is to remove the kind from that adapter rather than to add a second flag.

- **SNMP is spoken on port 161 and nowhere else.** `collector/snmp/session.py` holds the port as a constant because `devices` has no column for another one, so a device whose agent listens elsewhere cannot be walked. Adding a port is a device-table migration and an API contract change; it has not come up, and inventing the column before it does would be guessing at whether it belongs on the device or on the credential profile.

- **NetShield does not speak SNMPv1.** `CommunityData` is built with `mpModel=1`, which is v2c. `CredentialKind` has no v1 member and SPEC.md §2 describes a modern estate, so this is a consequence of a decision already made rather than a gap — but a genuinely old device in a real estate would be unreachable and would fail its walk with an authentication error rather than with anything that says why.

- **`ruff`'s S508 is suppressed at one line.** The rule objects to SNMPv2c on principle and is right to; it is suppressed in `_auth_data` because WP-1.2 settled that a credential profile may be `SnmpV2c`, and refusing the kind in the collector would mean the API can store a credential that nothing will use. The on-demand walk prefers a v3 profile wherever a device has one, and the community string is a `SecretStr` the whole way. Revisit if the estate is ever known to be v3-only.

- **`pysnmp` ships no type information, and one module is exempted from a strict flag because of it.** `disallow_any_unimported` is relaxed for `collector.snmp.session` alone — the single module that imports the library — and `ignore_missing_imports` is set for `pysnmp.*`. Everything above that module is checked at full strength, and a test asserts that no other collector module imports `pysnmp` at all, which is what makes the exemption's scope real rather than nominal. A stub package would remove the need; none exists.

- **An interface that disappears is deleted, so there is no port history.** `device_interfaces` is derived data with no soft delete: a walk that read the whole table removes the rows it did not see. `first_seen_at` survives across walks, so "this port appeared last Tuesday" is answerable, but "this port was removed last Tuesday" is not. That is deliberate — an interface that has genuinely gone is noise in every list it would otherwise stay in — and if Phase 2's topology or Phase 6's alerting wants to notice a port disappearing, `DeviceFingerprinted` is published when the set changes and is the seam to hang it from.

- **`sysName`, `sysContact` and `sysLocation` are recorded and read by nothing.** They are on `device_fingerprints` because a walk that has them should not throw them away — `sysLocation` in particular is a candidate for the free-text `devices.site` an operator fills in by hand. Nothing reconciles them, deliberately: "the device thinks it is in Rack 3 and the inventory says Rack 4" is a disagreement to show a person, not one to resolve silently.

- **Uptime is what the agent said, and `sysUpTime` wraps.** It is a 32-bit counter of hundredths of a second, so it turns over after about 497 days, and a device that has been up longer reports a small number. Nothing reconstructs a boot time from it and nothing should without a second observation to disambiguate the wrap. Phase 3, which will sample it on an interval, is where that becomes both possible and worth doing.

- **A walk is bounded per device and not in aggregate.** *(WP-1.6 answered the scheduler half and not the route half: the discovery schedule has `MaxRunsPerScan`, `MaxJobsPerRun` and `MaxAddressesPerRun`, and the run route still lets one caller start a run of every seed at once — see the discovery rate-limiting note above. The original note follows.)* One outstanding walk per device is refused with a `409`, which stops a person clicking twice, but nothing stops the same person walking five hundred devices in five hundred requests. Sign-in is not rate limited either (below) and the two belong to the same missing story. At WP-1.5's scale — a walk is asked for by a human — it is theoretical; when WP-1.6 schedules walks it will not be, and the scheduler needs its own ceiling the way `ReachabilityOptions.MaxJobsPerScan` has one.

- **Every subtree walk that fails, fails the whole job.** A device with no ENTITY-MIB answers the walk with nothing and is handled correctly, but a device that *times out* partway through the ENTITY-MIB subtree fails the walk outright — even though the system group had already answered and the vendor had already been resolved. Failing is the safe direction, because a partial walk applied as if complete would delete interface rows it never read. A more forgiving version would need per-subtree outcomes in the result payload, which is a contract change nobody has needed yet.

- **`CollectorJobOptions.MaxAttempts` governs a walk as it governs everything else.** A walk somebody is waiting for arguably deserves fewer retries than a background probe, and `DiscoveryOptions` deliberately has no `MaxAttempts` of its own: giving one kind its own count means widening `NewCollectorJob` and the queue behind it, which is the job-contract seam WP-1.5 had no instruction to touch. Worth revisiting in the package that first has a reason.

- ~~**A device with several SNMP profiles gets the one the fixed rule picks.**~~ **Answered in WP-1.6.** The rule moved from `QueueDeviceWalkHandler` into `SnmpCredentialSelector` and reads `Inventory:Discovery:CredentialKindOrder`, defaulting to the WP-1.5 order. It is an order over credential *kinds* and not a list of profile ids, so it cannot be used to hand a collector a credential the caller could not otherwise reach — see `DECISIONS.md`. An operator still cannot say "walk *this* device with *that* profile", which would need the per-device override this note originally imagined. The original note follows.

- **A device with several SNMP profiles gets the one the fixed rule picks.** SNMPv3 before SNMPv2c, then the earliest assignment, then the id — deterministic, and secure by default, but an operator cannot say "walk this device with that profile". WP-1.6's entry names "credential profile order" as part of its seed configuration, and that is the package that should make the rule configurable; `QueueDeviceWalkHandler.ChooseCredentialAsync` is the one place it lives.

- **The `DiscoveryRun` permission now has its first endpoint, and it is coarse.** It was declared in WP-0.5 as "start a discovery run outside its schedule" and had no route until now. Holding it means being able to make NetShield open a credential and read any device in the estate, which the Operator role can do and the Analyst cannot — a defensible reading, but the first time that permission has actually decided anything. WP-1.6 will hang the range sweep off the same permission and should confirm both are meant to be the same privilege.

- ~~**`Discover` has a producer but no schedule.**~~ **Answered in WP-1.6**: `DiscoverySchedulePass` sweeps seeded ranges on a timer through `EnlistAsync`, exactly as this note proposed, and produces reviewable candidates. `ConfigFetch` still has no producer and will not until Phase 7. The original note follows.

- **`Discover` has a producer but no schedule.** WP-1.5 added `POST /api/v1/devices/{id}/walk`, which queues one `Discover` because a person asked. That is a fingerprint refresh of a device already in the inventory, not a discovery run: nothing sweeps a range, nothing runs on a timer, and there is no candidate to review. WP-1.6 owns all of that, and `ICollectorJobQueue.EnlistAsync` is the seam its scheduler should use — `EnqueueAsync` is what the on-demand route uses, because it has nothing else to commit alongside. `ConfigFetch` still has no producer and will not until Phase 7.

- ~~**`ExecutorRegistry` is keyed by job kind, and two kinds now have one executor each.**~~ **Answered in WP-1.6** by the discriminator-level registry this note proposed: `DiscoverExecutor` holds `DISCOVER` and dispatches on `parameters.walk` to the SNMP walk or the range sweep. No `CollectorJobKind` member was added and the collector's wire contract is untouched. WP-3.2's SNMP metric polling has the same problem for `POLL` and now has a worked example of the answer. The original note follows.

- **`ExecutorRegistry` is keyed by job kind, and two kinds now have one executor each.** `IcmpExecutor` holds `POLL` and `SnmpWalkExecutor` holds `DISCOVER`, and `ExecutorRegistry.register` refuses a second executor for a kind. So WP-3.2's SNMP metric polling cannot simply add an executor beside the ICMP one, and **WP-1.6's range sweep cannot add one beside the walk**. The discrimination already exists a level down and is now used twice: `parameters.probe` for a `Poll`, `parameters.walk` for a `Discover`, with each executor refusing a job that names another. The cheapest fix in both cases is a discriminator-level registry inside the one executor for that kind, keyed on the same member the API's result handlers already filter on; adding a `CollectorJobKind` member would be a change to the collector contract and needs the human's instruction. Still deliberately not built ahead of the package that needs it — but WP-1.6 is now the first package that will.

- **A reachability probe needs an ICMP socket, and a deployment has to grant one.** The collector tries `SOCK_DGRAM`/`IPPROTO_ICMP` first — unprivileged, and available wherever `net.ipv4.ping_group_range` includes the running group — and falls back to `SOCK_RAW`, which needs `CAP_NET_RAW`. If neither opens, every probe job fails with a message naming both, and device state is deliberately left untouched rather than every device being reported offline. Development works as-is on a normal Linux host (`ping_group_range` is `0 2147483647` on the machine this package was built on). A container gets neither by default: WP-8.7's `docker-compose.yml` has to set `sysctls: net.ipv4.ping_group_range: "0 2147483647"` on the collector service, or add `cap_add: [NET_RAW]`, and the first is the least-privilege answer. This belongs with the deployment story alongside the three secrets that have the same gap.

- **Five inventory enums are written as ordinals on the wire.** `DeviceState`, `DeviceVendor`, `DeviceRole`, `CriticalityTier` and `DeviceEnvironment` carry no type-level `[JsonConverter]`; they are listed in `InventorySerializerContext`'s `JsonSourceGenerationOptions.Converters`, and that list does not take effect when the context is one resolver among several on the host's JSON options. So `GET /api/v1/devices/{id}` answers `"state": 1`, and the committed `openapi/v1.json` says `{"type": "integer"}` for all five. Every enum that carries the attribute on the type itself — `UserRole`, `Permission`, `CredentialKind`, `CollectorJobKind`, the two SNMP algorithms — is correctly written as its name. This contradicts the WP-0.4 decision that an enum travels as its name so that inserting a member cannot change what a stored response meant, and inserting a `DeviceVendor` today would silently renumber every response already captured. **This is a WP-1.1 defect, found by WP-1.4 and not fixed by it**: the fix is five one-line attributes, but it changes the API contract, `openapi/v1.json` and the generated TypeScript client, which is a diff WP-1.4 has no instruction to make. WP-1.7 is the natural owner, since it is the package that renders all five. The database is unaffected — every one of these is stored as its name by `HasConversion<string>()`.

- **Nothing exposes reachability detail over the API.** `devices.state` is on `DeviceSummary` and `DeviceDetail` and moves correctly, but the last round trip, the last loss percentage, when the device was last probed, when its state last changed, and `last_error` when the collector could not probe it are all on `device_reachability` and reachable only from the database. WP-1.7's device screen is what needs them — and `last_error` in particular, because "this device has not been probed since Tuesday" currently presents as a device that is confidently Online with a stale `last_probe_at`.

- **A device state transition writes no audit row.** It is not an API call by an actor: the observation comes from a machine on a poll interval, and WP-1.3 already settled that collector data-plane traffic does not go in `audit_log`. `DeviceStateChanged` on the outbox is the record, and Phase 6's alerting is what subscribes to it. If an investigation ever needs "when did this device go down" from the audit log rather than from the event stream, that is a deliberate decision to make then, and it would be one row per transition rather than one per probe.

- **Reachability throughput is not provisioned for the target estate.** `SPEC.md` §1 designs for 500 devices on a sixty-second interval — 8.3 probes a second — while one collector's defaults lease at most 25 jobs every 15 seconds, which is 1.7 a second. The queue would grow, and the scheduler's skip-if-outstanding rule would then quietly stretch every device's real interval rather than piling rows up. Nothing is wrong in the code; the defaults simply have not been sized against the target, and the honest fix is a capacity exercise (raise `MaxJobsPerLease`, shorten `PollSeconds`, or run more collectors) belonging to whoever first runs a full-size estate. A collector's capacity is 8 concurrent jobs by default, which a four-request probe at 0.25 s spacing occupies for about three seconds.

- **A reachability probe interprets no ICMP error message.** A Destination Unreachable, a TTL Exceeded or an Administratively Prohibited is counted as no reply, the same as silence. That is honest — the device did not answer — but it discards a real distinction an operator would want: "the router says there is no route" is a different fault from "nothing came back". Growing `packet.py` into something that reads embedded original headers out of ICMP errors is a general-ICMP-library job, and it was deliberately not started. Worth revisiting if reachability alerting in Phase 6 wants to say why.

- **An IPv6 link-local address cannot be probed.** The probe connects with a two-tuple and supplies no scope id, so `fe80::/10` fails. No device in the inventory can be one today — `primary_ip_address` is the address NetShield reaches a device on, and a link-local address is not routable from the collector's network — but the failure would present as a failed job with a socket error rather than as a clear refusal.

- **One audit row per released credential is bounded by the job rate, not by the estate.** At WP-1.3's scale that is nothing; at `SPEC.md` §1's target — 500 devices polled on a 60-second interval — an SNMP poll carrying a credential would be on the order of 700,000 `audit_log` rows a day, which is the volume problem the `[NoAudit]` decision was made to avoid. Phase 3's polling package should decide whether a poll credential release is still worth a row each, or whether the trail should be per collector per interval. Nothing needs changing before then, and the decision belongs to the package that creates the volume.

- **A collector job keeps its result for ever, and WP-1.4 started actually writing them.** `collector_jobs` has no retention policy and no `deleted_at`; a finished job is a record of work that a `SPEC.md` §2 retention policy should eventually prune, and the policy table that would drive it does not exist until WP-1.6 and Phase 8. This stopped being hypothetical with the reachability schedule: a 500-device estate probed every minute writes about 700,000 rows a day, each carrying a per-request round-trip payload. It is a real capacity question rather than a tidiness one, and it is now on a clock.

- **The collector's shared secret reaches development and nothing reaches a deployment.** Exactly the gap `Identity:Seed:Password` and the key-encryption key have, and it should be closed once for all three rather than three times. `aspire run` generates it and persists it to the AppHost's user-secrets store; a deployment must supply `Collector:SharedSecret` to the API and `NETSHIELD_COLLECTOR_SECRET` to every collector, from the same secret store, and there is no rotation story — changing it means restarting both sides. The package that writes the deployment story owns all of this.

- **`--migrate` and `--rewrap` still have no automated test of their argument dispatch**, unchanged from WP-1.2. WP-1.3 added no third mode, so the threshold that would make extracting the dispatch worthwhile has not been crossed.

- **`aspire run` could not be verified end to end in this session's sandbox.** The stack comes up, the migration applies `collector_jobs` and `collectors`, `uv sync` succeeds and the `collector` resource is correctly registered and waiting — but `web-host` never reports healthy here, because its `/health/ready` probe is HTTPS and the developer certificate is only partially trusted in this environment (`PartiallyFailedToTrustTheCertificate`). `web-client`, which has had the same `.WaitFor(webHost)` since WP-0.7, sits in `Waiting` alongside it, so this is a pre-existing property of the sandbox rather than anything WP-1.3 changed. The live collector-to-API loop is step 1 of this package's manual checklist and needs a human on a machine with a trusted dev certificate.

- **The key-encryption key reaches development and nothing reaches a deployment.** Exactly the gap `Identity:Seed:Password` has. `aspire run` generates 32 random bytes, base64-encodes them and persists them to the AppHost's user-secrets store, so the key survives a restart and the credentials sealed under it stay readable. A deployment has to supply `Security:CredentialEncryption:ActiveKeyId` and `Security:CredentialEncryption:Keys:{id}` itself, from a secrets manager, a mounted file, or a KMS — and it must not keep the key beside the database whose rows it opens, which is the whole point of the envelope. `Base64KeyParameterDefault.WriteToManifest` deliberately writes no default for that reason: a manifest that told the deployer to generate the key would be making the wrong promise. Nothing in this package invents the delivery mechanism; the package that writes the deployment story owns it.

- **`AuthenticatedUser.mustChangePassword` trips the redaction name rule.** The new `ApiSecretExposureTests` gate found it on its first run. The member is a boolean and carries no secret, but `SecretRedactor` blanks by name — which is why WP-0.5 named the equivalent audit member `changeRequired` — so anything that ever logs the shape as structured state records `[REDACTED]` for it. Renaming it is a change to the auth contract and to the SPA that reads it, which WP-1.2 has no instruction to make, so it is exempted by name in that test with the reason written down. The next package that touches the auth contract should decide whether to rename it to `passwordChangeRequired`.

- **Credential profile reads are behind `CredentialsManage`, which is Administrator-only.** There is no `CredentialsRead` permission, and adding one would be a change to the RBAC table WP-1.2 was not told to make; meanwhile a profile's username is half of an SSH credential and the list of names says which accounts NetShield holds passwords for, so over-restricting was the recoverable choice. If WP-1.7's device screen needs to show an Operator which credential a device uses, adding `CredentialsRead` and moving the two read routes onto it is the change — and it is a `[SENSITIVE]` one.

- **The decrypt path has no production call site.** `ICredentialResolver` is built, internal, and covered by integration tests that resolve it out of the container by hand, but nothing in the running system calls it — the same shape `RequirePermission` was in after WP-0.7. WP-1.3's collector-job endpoint is what proves it in anger, and it also owns the decision about how far to widen the visibility. The resolver deliberately does not choose between a device's several credentials: `ForDeviceAsync` lists what a device has by id and kind without decrypting anything, and `ResolveAsync` opens one named profile. Which credential a given job should use is scheduling policy, and WP-1.3 and WP-1.6 own it.

- **A soft-deleted profile keeps its sealed material.** Deleting a profile hard-deletes every assignment of it and soft-deletes the row, so nothing can reach the credential and no collector will be handed it — but the ciphertext stays in the column, and `--rewrap` keeps moving it so the old key can still be retired. Actually erasing the bytes is a shredding policy with its own retention question and its own audit story, and it is not a line to slip into a delete handler.

- **Neither `--migrate` nor `--rewrap` has an automated test of its argument dispatch.** Both are verified by running them. `MigrationMode` and `RewrapMode` are internal to `NetShield.Web.Host` and `ARCHITECTURE.md` §4 lets nothing reference that project, so the pieces behind each switch are tested (`CredentialKeyRewrapper` has five integration tests) while the two lines in `Program.cs` that reach them are not. If a third mode appears, that is the point at which the dispatch is worth extracting somewhere testable.

- **A rotation deliberately does not touch `updated_at`.** Nothing about a profile as an operator understands it has changed, and a re-wrap that stamped every row would look like an estate-wide edit in every list sorted by it. The consequence is that a rotation is invisible in the profile list; the audit row under `inventory.credential-rewrap` is where it is visible.

- **The guard's error state names the API, not the fault.** A non-401 failure of `GET /auth/me` renders `SessionUnavailable` — "NetShield is not responding", with a retry — because a reader can act on a service that has not started and cannot act on a parse error. That means a genuinely malformed response is reported as an outage. It is the right trade for the two causes seen so far (no dev proxy, API still starting); if a third cause appears that a reader could act on differently, this is the screen to split.
- **Three navigation permission mappings are provisional.** `Security › Posture → ComplianceRead`, `Security › Findings → VulnerabilitiesRead` and `Threats → AlertsRead`. None of those three surfaces is named by `SPEC.md` §2 — Security's children are WP-0.6 placeholders and Threats comes from the reference screenshot — so the gates are the most defensible reading of what each screen will show rather than a settled decision. The Phase 7 package that names the security posture surface owns revisiting all three, alongside renaming the routes. Every other mapping comes straight from the area the destination belongs to.
- **`RequirePermission` has no production call site.** The primitive and its hook are built and tested, because "a Read-only user sees no write controls" needs somewhere to live and the sidebar is the only thing WP-0.7 could apply it to — the SPA has no write control yet. The first package to add one (WP-1.1's "Add device") is what proves it in anger, and must still declare the permission at the endpoint: hiding is presentation, and `ARCHITECTURE.md` §8 checks at the endpoint and again in the module.
- **A hidden destination is still a reachable route.** The sidebar draws only what the session holds a permission for, but typing the address arrives at the screen — deliberately, so that nothing on the client side can be mistaken for the boundary. The screen is empty today; once a screen queries something, the API's 403 is what the user meets, and each package has to decide how its screen renders that.
- **The sign-in and change-password screens have no reference to be measured against.** `docs/design/reference-dashboard.png` shows one signed-in dashboard and nothing else, and `DESIGN.md` §9 forbids inventing a visual direction — so both screens are assembled from §3–6 primitives already in the theme and nothing else. That is the most faithful reading available, not a verified match. If a signed-out reference is ever drawn, these two are the screens to hold against it.
- **Sign-in is not rate limited, and WP-0.7 has now given it a public front door.** The gap was recorded in WP-0.5 and is unchanged, but until this package there was no page from which to spend an Argon2id verification. Lockout still bounds attempts against one account; nothing bounds attempts across many accounts from one source.
- **The return path is sanitised at the point of use, not by `validateSearch`.** A TanStack Router route inherits its parent's search parameters and merges its own over them, so a value the child's `validateSearch` rejected is still present as the root parsed it. `safeReturnPath` is therefore applied where the value is read. Any later route that reads a URL parameter and acts on it has the same trap waiting.
- **The session query is nullable below the guard, and one component leans on it.** `_app` resolves the session before the shell renders, so there is always one — except in the frame between signing out and the redirect landing, when the cache is empty and the shell is still mounted. `useSession` returns `undefined` there, `usePermissions` holds nothing, and `UserBlock` draws nothing. A future component below the guard has to tolerate the same gap; a hook that promised a user would have to suspend with no boundary above it or assert past the gap, and both turn a one-frame absence into a render loop.
- **Nothing hides a route from the router, only from the sidebar.** There is no per-route permission declaration and no 403 screen. If a later package wants a screen to refuse before it renders, `_app`'s `beforeLoad` is where that goes, and it needs a designed "you cannot see this" state — which `DESIGN.md` does not have.
- **The reference dashboard's content is not built.** WP-0.6 built the chrome — sidebar, header, routing, theme — and every route renders a placeholder. The KPI strip, topology canvas, bandwidth chart, security donut, recent-alerts table, top-applications donut and device-health list in `docs/design/reference-dashboard.png` are the dashboard work in Phase 8, and Recharts, React Flow and `dagre` are deliberately not installed yet.
- **The notification bell shows no count.** `NotificationBell` takes one and renders the badge when it is above zero; nothing counts anything until the alerting work in Phase 6. The reference screenshot shows `12`, and inventing a number to match it would have been worse than the gap.
- **`Security ›` has invented children.** The screenshot shows the chevron but not what is behind it, and `SPEC.md` §2 has no Security area of its own. `/security/posture` and `/security/findings` are placeholders chosen so the section is not a chevron over nothing; whichever Phase 7 package builds the posture surface should rename them. Reports and Administration children come straight from `SPEC.md` §2 and need no such warning.
- **Light mode is derived, not designed.** `DESIGN.md` §2 makes the toggle V1 scope and says light is derived from the dark tokens. `theme.css` derives it by moving only the surface and text roles and leaving every semantic hue alone. It has never been looked at against a reference, because there is no light reference. The `[data-theme='light']` block is the only place in the SPA holding a colour `DESIGN.md` §3 does not name, and the token test exempts it for exactly that reason.
- **No SignalR.** `ARCHITECTURE.md` §9 gives the SPA one connection with per-route topic subscriptions. Nothing publishes yet, so nothing subscribes; the package that first has a live stream to push owns standing the connection up.
- **The SPA build writes into `src/NetShield.Web.Host/wwwroot`, which is git-ignored.** That is deliberate — nothing copies the build, so nothing can copy a stale one — but it means `dotnet publish` on its own produces a host with no SPA in it. The package that writes `docker-compose.yml` has to run `npm run build --prefix src/NetShield.Web.Client` before publishing the host, or add an MSBuild target that does.
- **Regenerating the API contract is a two-step manual flow.** Change an endpoint, run the suite once with `NETSHIELD_UPDATE_OPENAPI=1` to rewrite `openapi/v1.json`, then `npm run api:generate --prefix src/NetShield.Web.Client` to rewrite `schema.d.ts`, then commit both. Two tests fail until you do, which is the point, but a single `regen` script would be kinder and belongs with whoever next changes the contract.
- **The OpenAPI document is produced by a test host, not by the composition root.** `ARCHITECTURE.md` §4 lets nothing reference `NetShield.Web.Host`, and build-time document generation would run `Program.cs` without the Aspire connection strings it demands. `ApiDocumentParityTests` fails if `Program.cs` maps an endpoint group the document host does not, which closes the obvious hole; the cost is that a second file has to gain a line whenever a module's endpoints are first mapped.
- **`MapNetShieldSpa` lives in `NetShield.Platform`, not in `Web.Host`.** Same reason: "the shell is reachable without a session" is worth an integration test and nothing may reference the composition root. `ARCHITECTURE.md` §4 describes Platform as cross-cutting and does not list SPA hosting; if that reads as a stretch, the alternative is to leave the claim untested.
- **A resource name with a hyphen cannot reach a process npm starts.** Aspire names a service-discovery variable after the resource, so `web-host` produces `services__web-host__http__0` — and `npm run dev` runs its script through `sh -c`, where a POSIX shell exports only names that are valid shell identifiers. The variable is silently dropped between `sh` and `node`. The AppHost therefore also passes `NETSHIELD_API_URL`, and `OrchestrationTests` fails if that goes missing or if the resource is ever renamed to something a shell would have carried. Any future resource started through a shell has the same trap; Aspire's own `WEB_HOST_HTTP` (uppercased from the resource name) is an alternative, but it changes silently when the resource is renamed. Running the SPA without `aspire run` still needs `NETSHIELD_API_URL` set by hand.
- **Two npm packages are pinned below their latest major.** `typescript` is held at 5.9 because `typescript-eslint` 8 does not accept 6.x yet. Worth revisiting when it does.
- **The 1536px layout has not been checked in a browser by the agent.** There is no headless browser on this machine — Playwright's Chromium needs system libraries that require `sudo` to install — so "matches the reference at 1536px" is on the manual checklist rather than in a test. A visual-regression check is worth a package of its own once the dashboard content exists to regress.
- **There is no user administration.** Nothing creates, disables, renames or resets a second account — the seeded administrator is the only account the system can produce. Whichever package owns the Administration screen in Phase 8 needs user CRUD, an administrator-initiated password reset that sets `must_change_password`, and a way back in when the sole administrator is locked out.
- **Sign-in is not rate limited.** Lockout bounds attempts against one account; nothing bounds attempts across many accounts from one source, and nothing spends Redis on it yet. Worth a look when the rate-limiting story is written, since the Argon2id verification on every attempt is itself the expensive part.
- No authentication event reaches the outbox. WP-0.5 records sign-in, lockout and password change in `audit_log`, which is the human-facing record; `UserSignedIn`, `AccountLockedOut` and `PasswordChanged` as integration events are still unbuilt, and are what a notification rule in Phase 6 would subscribe to. The audit row is not a substitute — nothing subscribes to a table.
- `Identity:Seed:Password` reaches `Web.Host` as an environment variable from an Aspire parameter persisted to the AppHost's user secrets. Deployment has no equivalent yet; the package that writes `docker-compose.yml` has to decide how a mounted secret gets there, and the same question covers the credential KEK in WP-1.2.
- The Argon2id work factor is a single global setting. Raising it rehashes each account on its next sign-in and never on its own, so an account that has not signed in since a change keeps the older cost until it does.
- **The lab is still not stood up, and WP-1.5 shipped without it.** The seven walk fixtures under `src/netshield-collector/tests/fixtures/snmp/` are hand-authored from documented `sysObjectID` arcs and `sysDescr` formats, clearly marked synthetic, and they prove exactly what they can prove: that the resolver reads those two fields correctly and that each adapter extracts the three facts from the right place. What they cannot prove is that a real agent's `sysDescr` matches the format its vendor documents, that a real `entPhysicalTable` puts the chassis where expected, or that a private OID is answered at all. Containerlab plus an `snmpsim` corpus (see `WORKFLOW.md` § Test data) is what closes that, and replacing a fixture file with a real recording of the same platform should change nothing but realism — the format is the contract. Worth doing before Phase 2's neighbour collection, which reads far more vendor-variable tables than this package does.
- `docker-compose.yml` is in the `CONVENTIONS.md` §1 layout and `ARCHITECTURE.md` §2 names Docker Compose as the deployment orchestrator, but no Phase 0 package creates it. It needs a package of its own, most naturally in Phase 8 alongside hardening.
- **`dotnet test` now needs a Docker daemon** for `NetShield.IntegrationTests` alone. WP-0.3 gave that project its first tests and the Testcontainers dependency `CONVENTIONS.md` §7 requires; unit and architecture tests stay container-free, so a layer can still be run on its own. The WP-0.2 "Done when" criteria — dashboard health, `/health`, `/health/ready`, and the `timescaledb` extension version — are still verified by hand rather than by a test, and the harness to automate them now exists.
- `WORK_PACKAGES.md` WP-0.2 names **MailHog**; the build uses **MailPit** (`axllent/mailpit:v1.31.0`) instead. MailHog was archived upstream in 2024 at v1.0.1. MailPit is the maintained drop-in with the same SMTP-sink and web-UI role, and it ships a `/readyz` endpoint that lets the dashboard report the resource healthy. The WP text has not been edited; this note is the record of the deviation.
- `ServiceDefaults.MapDefaultEndpoints` maps the health endpoints in the Development environment only, which is the Aspire template's default and the reason a `dotnet run` outside Aspire answers 404 there. A Docker Compose deployment will need container health checks against these paths, so the package that writes `docker-compose.yml` has to decide deliberately whether to expose them in production and on which interface.
- `NetShield.UnitTests` reaches the Postgres container's resolved environment through `GetEnvironmentVariableValuesAsync`, which Aspire 13.5.3 marks obsolete; its replacement, `ExecutionConfigurationBuilder`, is not public in that version. The call is behind a scoped `#pragma` in `AppHostModel`. Revisit when Aspire makes the replacement public.
- The AppHost pins `timescale/timescaledb:2.29.0-pg17` and `axllent/mailpit:v1.31.0` by literal; Redis floats on the Aspire default (8.6 today). Container image versions have no equivalent of `Directory.Packages.props` and nothing yet updates them.
- The `ARCHITECTURE.md` §4 module rules are enforced over the **project-reference graph**, not over loaded assemblies, because a reference an empty project declares is elided from assembly metadata and a reflection rule would pass over all ten modules vacuously. Two §4 rules are therefore still unenforced and need an assembly-level rule library (NetArchTest or ArchUnitNET) in WP-1.1, once a module holds real types: *cross-module communication carries `Contracts` types only*, and *no module exposes an EF entity across its boundary*.
- **Migrations are applied by `NetShield.Web.Host --migrate`, not on startup** (settled in WP-1.1). The same artifact, run with an argument, applies `PlatformDbContext`, `IdentityDbContext` and `InventoryDbContext` in that order — Platform first, because it owns `outbox_messages`, which the Inventory context maps and excludes from its own migrations — then starts the host just long enough for the first-run seeder to run, then exits. It is a generic host and binds no socket. The AppHost runs it as the `db-migrator` resource and `web-host` `WaitForCompletion`s it, so `aspire run` on an empty volume comes up migrated and with an administrator. It is idempotent: a second run reports each context up to date and seeds nothing. **Deployment still has no equivalent** — the package that writes `docker-compose.yml` has to run the same image with the same argument as a one-shot service before the API starts, and decide how the least-privilege DDL credential differs from the API's.
- `IntegrationEventRegistry` keys an outbox row by the event type's `FullName`, so moving or renaming an event type is a breaking change for rows still in flight. Fine while nothing is deployed; revisit before the first release if event types look likely to move.
- The outbox dispatcher assumes it is the only one running — it claims rows with a plain query rather than `FOR UPDATE SKIP LOCKED`. Correct for the single-node V1 in `SPEC.md` §3, and the reason `AddOutboxDispatcher` is a separate opt-in call that only `Web.Host` makes. A second dispatching process would double-deliver.
- Delivered outbox rows are kept, and nothing prunes them. They belong in the retention policy table `ARCHITECTURE.md` §3 describes, which arrives with the policy work in Phase 8.
- `OutboxPayload` uses reflection-based `System.Text.Json` rather than a source-generated context. `CONVENTIONS.md` §4 requires source generation for the API's JSON; these rows are internal and never leave the process, but the choice would have to be revisited if a NetShield process were ever published trimmed or AOT.
- `.editorconfig` carries placeholder sections for `*.py` and `*.{ts,tsx,...}` ahead of the collector (WP-1.3) and the SPA (WP-0.6). Revisit them when those toolchains land — `ruff` and Prettier own formatting there, not `dotnet format`.
- `Directory.Packages.props` now sets `CentralPackageTransitivePinningEnabled`, which surfaced two existing transitive downgrades and moved `Microsoft.Extensions.Hosting` from 10.0.0 to 10.0.11 to clear them. Every EF Core package is pinned at 10.0.11 and the local `dotnet-ef` tool was updated to match; a future `aspire update` has to keep the two in step.
- **The audit row is written after the domain change commits, not with it.** The middleware records once the endpoint has answered, in its own transaction, which is what lets it record a 401 or a 403 the endpoint never saw. A process death in the window between the two loses the row. Accepted deliberately (see `DECISIONS.md`); if audit ever has to be atomic with the change it describes, the answer is to route it through the transactional outbox, not to hand-write an append into every handler.
- **`source_ip` is the socket's remote address, with no forwarded-headers handling.** Behind a reverse proxy — which is how a Docker Compose deployment will run — every audit row would name the proxy rather than the user. The package that writes `docker-compose.yml` has to configure `UseForwardedHeaders` with a trusted-proxy list, and it must be a list rather than "trust everything", or the field becomes attacker-controlled.
- **Deny-by-default now applies to every endpoint added from here on.** An endpoint with no policy answers 401. WP-0.6's SPA hosting is the first thing this will bite: `MapFallbackToFile` and the static-file routes have to declare `AllowAnonymous()`, or the sign-in page itself will require a session.
- **Nothing reads the audit log.** `Permission.AuditRead` is defined, granted to the Administrator, and unused — there is no query endpoint and no screen. The Administration screen in Phase 8 owns both, and will need cursor pagination and filters by actor, action, target and time.
- **Nothing prunes `audit_log`.** Like the delivered outbox rows, these belong in the retention policy table `ARCHITECTURE.md` §3 describes. Unlike the outbox rows, pruning them is a policy decision with a compliance edge to it, and the database rule refuses a `DELETE` — whatever prunes it will have to drop the trigger, delete, and restore it, deliberately and audibly.
- **The `must_change_password` claim can go stale in one direction.** It is minted at sign-in and re-minted on refresh and on the change that clears it. An administrator setting the flag on somebody else's account mid-session would not refuse that session until it refreshes. Nothing can set it today; whichever package adds administrator-initiated password reset has to decide whether a forced reset also revokes the target's sessions.
- **The permission set is defined but barely exercised.** Only the test project's probe endpoints call `RequirePermission`, because no module endpoint exists yet. Every package from WP-1.1 on has to declare a permission per endpoint, and the first few will show whether the grain is right — it is much cheaper to split a permission now than after a dozen endpoints name it.
- `AuditPayload` serialises before/after with reflection-based `System.Text.Json`, the same choice and the same caveat as `OutboxPayload`: internal, never leaves the process, would have to be revisited if a NetShield process were ever published trimmed or AOT.
- The audit snapshot member names avoid the words `SecretRedactor` treats as secret — `changeRequired` rather than `mustChangePassword`. It works and it is documented at both call sites, but it is a trap for the next author, who will name a field honestly and find `[REDACTED]` in the column. Worth a lint or a test that fails when a snapshot key is one the redactor would blank.

- **The module-level `IResourceGuard` check is never the one that refuses, in practice.** Every device handler calls it, but the endpoint's `RequirePermission` has already refused the same caller, so the second check is dead weight on every request that reaches a handler. That is deliberate — ARCHITECTURE.md §8 wants it there for the batch operation or background job that has no endpoint in front of it — but it means no integration test can prove the module check works on its own, and `ResourceGuardTests` in the unit suite is the only thing that does. The first handler reached from something other than a route is what will prove it in anger.
- **`DeviceUpdated` fires even when nothing changed.** A PUT that sets every member to the value it already held still writes an outbox row and an audit row. Detecting a no-op would mean comparing the snapshot before and after, which is cheap — but "nothing changed" is a judgement about which fields count, and no subscriber exists yet to have an opinion. Worth revisiting when one does.
- **The device list counts every match on every page.** `totalCount` costs a second query per request. Cheap at 500 devices; the first thing to drop if the estate grows past what `SPEC.md` §1 designs for, and `CursorPage.TotalCount` is optional by design so nothing breaks when it goes.
- **Nothing bounds how many devices exist.** `SPEC.md` §1 targets 500 and nothing enforces it. A create loop would fill the table, and the audit and outbox rows with it. Whatever adds rate limiting to sign-in should look at the write endpoints too.
- **`site` and `owner` are free text, not entities.** `SPEC.md` §2 names sites in the inventory read permission, and WP-1.7 wants to filter by site — which works today only because the filter matches the string exactly, ignoring case. Two operators spelling one site differently produce two sites. A site aggregate is the fix, and it needs a package of its own; until then, the filter is as good as the typing.
- **The `inet` column's containment operators are unused.** `primary_ip_address` is `inet`, so `<<` against a CIDR is available and would be the natural way for WP-1.6 to ask "is this discovered host already a device". Nothing uses it yet, and EF cannot express it without raw SQL — the same reason its unique index is raw SQL.
- **The `Inventory_AddDevices` migration carries hand-written SQL.** The unique partial index on `primary_ip_address` is a `migrationBuilder.Sql` call, because EF refuses to index a property whose CLR type is not `IComparable` and `IPAddress` is not. It is therefore absent from `InventoryDbContextModelSnapshot`, so a later `dotnet ef migrations add` will neither drop it nor recreate it — which is what we want, but it does mean the model snapshot is not the whole schema for this table. Any later change to that index has to be written the same way.
- **`db-migrator` and `web-host` are the same project twice in the AppHost.** Aspire builds it once and runs it twice, which is the point, but the dashboard shows two resources with one source and a reader could mistake the migrator for a second API. It exits immediately, which is the tell.
