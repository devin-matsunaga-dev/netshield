## Completed packages

- **WP-0.1 — Solution skeleton** (2026-09-03, `feat/wp-0.1-skeleton`). `NetShield.sln` with 19 projects on `net10.0`: AppHost, ServiceDefaults, Contracts, Platform, Web.Host, Ingest, ten module projects under `src/Modules/`, three .NET test projects. `Directory.Build.props` owns the target framework, nullable, implicit usings, and warnings-as-errors; `Directory.Packages.props` owns every package version. Project references follow `ARCHITECTURE.md` §4 — no module references another module. Five tests in `NetShield.ArchitectureTests` enforce those MSBuild invariants against the project files on disk.

- **WP-0.2 — Aspire orchestration** (2026-09-03, `feat/wp-0.2-aspire`). `NetShield.AppHost` orchestrates PostgreSQL 17 on `timescale/timescaledb:2.29.0-pg17`, Redis 8.6 with snapshotting, and MailPit, each on a named volume (`netshield-postgres-data`, `netshield-redis-data`, `netshield-mailpit-data`). `Web.Host` takes `AddServiceDefaults()` plus the Aspire Npgsql and Redis client integrations, waits for all three resources, and is probed at `/health/ready`. `Ingest` is registered with `AddServiceDefaults()` only. `ServiceDefaults` now maps `/health` (liveness) and `/health/ready` (readiness) in place of the template's `/health` and `/alive`. Twenty-two tests: ten over the AppHost resource model, five over the health endpoints, two repository-wide guards against a hardcoded connection string, and the five WP-0.1 invariants.

- **WP-0.3 — Platform primitives** (2026-09-03, `feat/wp-0.3-platform`). `NetShield.Platform` now holds the seven primitives every later package builds on. `Result`/`Result<T>` with a typed `Error` and an `ErrorKind`-to-status-code table, mapped to HTTP by `ResultEndpointExtensions`. RFC 9457 problem details for both a handled failure and an unhandled exception, carrying `traceId` and never a stack trace, an exception message or a credential — registered for every environment, not just Production. Cursor pagination: `Cursor` encode/decode, `PageRequest` (default 50, max 200, over-max rejected rather than clamped) and `ToCursorPage`, returning the `CursorPage<T>` shape from `Contracts`. `IClock` over `TimeProvider`, normalised to UTC at the boundary. Secret redaction applied by replacing `ILoggerFactory`, so every provider — console, OpenTelemetry, and anything a later package adds — is covered without a call site remembering. The transactional outbox: `outbox_messages` (migration `Platform_AddOutbox`), `IEventBus` writing the row into the caller's transaction, `OutboxProcessor` delivering a batch, and `OutboxDispatcher` looping with backoff. `NetShield.ArchitectureTests` gained the `ARCHITECTURE.md` §4 module rules over the project-reference graph. 118 tests: 94 unit, 10 integration against Testcontainers PostgreSQL on the AppHost's TimescaleDB image, 14 architecture.

- **WP-0.4 — Identity domain and local authentication** (2026-09-03, `feat/wp-0.4-identity`). `NetShield.Identity` holds `users` and `refresh_tokens` (migration `Identity_AddUsersAndRefreshTokens`, its own history table `__ef_migrations_history_identity`). Argon2id hashing at the OWASP parameters, stored as a PHC string so the costs travel with the hash and a sign-in can rehash at the current work factor. A configurable password policy applied wherever a password is set, the seeder included. Cookie authentication with a short session cookie on `/` and a `Path`-scoped refresh cookie, both `HttpOnly`, `Secure`, `SameSite=Lax`, set in code and not bindable. Rotating refresh tokens stored only as a SHA-256 digest, with chain revocation on replay. Lockout after five consecutive failures for fifteen minutes. `POST /api/v1/auth/{login,refresh,logout,password}` and `GET /api/v1/auth/me`, FluentValidation at the boundary, a source-generated serialiser that deliberately cannot serialise a grant. A first-run administrator seeded only into an empty `users` table, from an Aspire-generated persisted secret parameter, forced to change its password. 220 tests: 148 unit, 57 integration against Testcontainers PostgreSQL, 15 architecture.

- **WP-0.5 — RBAC and audit log** (2026-09-03, `feat/wp-0.5-rbac-audit`). `Permission` in `Contracts` — 22 members, one per `SPEC.md` §2 area — and `RolePermissions` in `Platform`, the whole of NetShield's RBAC policy in one table. A session cookie carries a role and never a permission; permissions are resolved from the role on every request. Endpoint-level authorization through `.RequirePermission(...)`, backed by policies an `IAuthorizationPolicyProvider` materialises on demand. **The API denies by default**: the fallback policy refuses any endpoint that declares no authorization, and the two `ServiceDefaults` health endpoints say `AllowAnonymous()` explicitly. `PasswordChangeNotPendingRequirement` closes the WP-0.4 gap — a session owing a password change is refused everywhere except `/auth/password`, `/auth/me` and `/auth/logout`. The module-level second check of `ARCHITECTURE.md` §8 is `IResourceGuard.Require(permission, resourceType, resourceId)`, returning a `Result` and naming the refused resource on the audit row. `audit_log` (migration `Platform_AddAuditLog`) is a plain table, append-only in three independent ways: every property is `init`-only, `PlatformDbContext` exposes no `DbSet` for it, and a `BEFORE UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` trigger raises rather than silently discarding. Recording is automatic — middleware writes one row for every state-changing call including the ones authorization refused, with actor, source IP, action, target, outcome, status and trace id; a handler adds domain detail through `IAuditContext`, and every before/after value passes through `SecretRedactor` on the way in. 327 tests: 217 unit, 91 integration against Testcontainers PostgreSQL, 19 architecture.

- **WP-0.6 — SPA shell** (2026-09-03, `feat/wp-0.6-spa-shell`). `src/NetShield.Web.Client`: React 19, Vite 8, TypeScript strict with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`, ESLint at `strictTypeChecked` and Prettier owning format. Tailwind 4 with every `DESIGN.md` §3–4 token as the theme, loaded through `tailwind.config.ts` by `@config` so the binding sentence in `DESIGN.md` §2 stays literally true; the hex values live once, in `src/styles/theme.css`, as custom properties the light palette re-points. Inter self-hosted as variable woff2 from `@fontsource-variable/inter`, bundled — no font CDN. TanStack Router, file-based, 29 route files: the fourteen sidebar destinations from the reference screenshot, the fourteen children of the three expandable sections, and four index redirects. Sidebar (200/64px, brand block, 40px items with the 3px accent bar, sections whose chevron rotates 90°, collapse pinned at the bottom, collapsed state persisted) and header (search capped at 400px with a working ⌘K, notification bell, help, theme toggle, user block) built to `DESIGN.md` §5–6. Below 1024px the sidebar becomes an overlay drawer with a header control and a backdrop, per `DESIGN.md` §5. TanStack Query owns server state, with a per-feature key factory as the pattern. `Microsoft.AspNetCore.OpenApi` describes every `/api` path; `src/NetShield.Web.Host/openapi/v1.json` is committed, `src/api/schema.d.ts` is generated from it by `openapi-typescript`, and `openapi-fetch` is the only path to the API. Two gates keep that honest — a `NetShield.UnitTests` test regenerating the document and an architecture test that the document host maps what `Program.cs` maps, plus a Vitest test regenerating the client. `Web.Host` now serves the SPA from `wwwroot` with both fallbacks `AllowAnonymous()`, and an `/api` catch-all answering RFC 9457 rather than letting an unknown API path receive HTML. The AppHost runs the Vite dev server as a resource, so `aspire run` is still the whole stack. 396 tests: 336 backend (222 unit, 94 integration, 20 architecture) and 60 frontend, MSW at the network boundary and `axe-core` over the shell.

## In flight / noticed

Things spotted during a package that are out of its scope. Do not fix them in the current package — record them here and address them in a package of their own.

- **The reference dashboard's content is not built.** WP-0.6 built the chrome — sidebar, header, routing, theme — and every route renders a placeholder. The KPI strip, topology canvas, bandwidth chart, security donut, recent-alerts table, top-applications donut and device-health list in `docs/design/reference-dashboard.png` are the dashboard work in Phase 8, and Recharts, React Flow and `dagre` are deliberately not installed yet.
- **The notification bell shows no count.** `NotificationBell` takes one and renders the badge when it is above zero; nothing counts anything until the alerting work in Phase 6. The reference screenshot shows `12`, and inventing a number to match it would have been worse than the gap.
- **`Security ›` has invented children.** The screenshot shows the chevron but not what is behind it, and `SPEC.md` §2 has no Security area of its own. `/security/posture` and `/security/findings` are placeholders chosen so the section is not a chevron over nothing; whichever Phase 7 package builds the posture surface should rename them. Reports and Administration children come straight from `SPEC.md` §2 and need no such warning.
- **Light mode is derived, not designed.** `DESIGN.md` §2 makes the toggle V1 scope and says light is derived from the dark tokens. `theme.css` derives it by moving only the surface and text roles and leaving every semantic hue alone. It has never been looked at against a reference, because there is no light reference. The `[data-theme='light']` block is the only place in the SPA holding a colour `DESIGN.md` §3 does not name, and the token test exempts it for exactly that reason.
- **No SignalR.** `ARCHITECTURE.md` §9 gives the SPA one connection with per-route topic subscriptions. Nothing publishes yet, so nothing subscribes; the package that first has a live stream to push owns standing the connection up.
- **The SPA build writes into `src/NetShield.Web.Host/wwwroot`, which is git-ignored.** That is deliberate — nothing copies the build, so nothing can copy a stale one — but it means `dotnet publish` on its own produces a host with no SPA in it. The package that writes `docker-compose.yml` has to run `npm run build --prefix src/NetShield.Web.Client` before publishing the host, or add an MSBuild target that does.
- **Regenerating the API contract is a two-step manual flow.** Change an endpoint, run the suite once with `NETSHIELD_UPDATE_OPENAPI=1` to rewrite `openapi/v1.json`, then `npm run api:generate --prefix src/NetShield.Web.Client` to rewrite `schema.d.ts`, then commit both. Two tests fail until you do, which is the point, but a single `regen` script would be kinder and belongs with whoever next changes the contract.
- **The OpenAPI document is produced by a test host, not by the composition root.** `ARCHITECTURE.md` §4 lets nothing reference `NetShield.Web.Host`, and build-time document generation would run `Program.cs` without the Aspire connection strings it demands. `ApiDocumentParityTests` fails if `Program.cs` maps an endpoint group the document host does not, which closes the obvious hole; the cost is that a second file has to gain a line whenever a module's endpoints are first mapped.
- **`MapNetShieldSpa` lives in `NetShield.Platform`, not in `Web.Host`.** Same reason: "the shell is reachable without a session" is worth an integration test and nothing may reference the composition root. `ARCHITECTURE.md` §4 describes Platform as cross-cutting and does not list SPA hosting; if that reads as a stretch, the alternative is to leave the claim untested.
- **A standalone `npm run dev` proxies nowhere.** The Vite dev server learns the API's address from the Aspire service-discovery variable, and `SPEC.md` §5 leaves no fallback in the repository. Running the SPA without `aspire run` needs `NETSHIELD_API_URL` set by hand.
- **The header's user block reads `GET /auth/me` and does nothing else with the answer.** It was the shortest honest way to prove the generated client is wired. It shows "No session" when the call is refused, does not redirect, does not guard a route, and does not hide anything by role — all of which is WP-0.7.
- **Two npm packages are pinned below their latest major.** `typescript` is held at 5.9 because `typescript-eslint` 8 does not accept 6.x yet. Worth revisiting when it does.
- **The 1536px layout has not been checked in a browser by the agent.** There is no headless browser on this machine — Playwright's Chromium needs system libraries that require `sudo` to install — so "matches the reference at 1536px" is on the manual checklist rather than in a test. A visual-regression check is worth a package of its own once the dashboard content exists to regress.
- **`must_change_password` is enforced, but WP-0.7 still owes the screen.** WP-0.5 refuses every authenticated route except `/auth/password`, `/auth/me` and `/auth/logout` while the flag stands, and `GET /auth/me` reports it. The SPA has to read that and send the user to a change screen; until it does, a seeded administrator's first session answers 403 to everything and the client has no idea why.
- **There is no user administration.** Nothing creates, disables, renames or resets a second account — the seeded administrator is the only account the system can produce. Whichever package owns the Administration screen in Phase 8 needs user CRUD, an administrator-initiated password reset that sets `must_change_password`, and a way back in when the sole administrator is locked out.
- **Sign-in is not rate limited.** Lockout bounds attempts against one account; nothing bounds attempts across many accounts from one source, and nothing spends Redis on it yet. Worth a look when the rate-limiting story is written, since the Argon2id verification on every attempt is itself the expensive part.
- No authentication event reaches the outbox. WP-0.5 records sign-in, lockout and password change in `audit_log`, which is the human-facing record; `UserSignedIn`, `AccountLockedOut` and `PasswordChanged` as integration events are still unbuilt, and are what a notification rule in Phase 6 would subscribe to. The audit row is not a substitute — nothing subscribes to a table.
- `Identity:Seed:Password` reaches `Web.Host` as an environment variable from an Aspire parameter persisted to the AppHost's user secrets. Deployment has no equivalent yet; the package that writes `docker-compose.yml` has to decide how a mounted secret gets there, and the same question covers the credential KEK in WP-1.2.
- The Argon2id work factor is a single global setting. Raising it rehashes each account on its next sign-in and never on its own, so an account that has not signed in since a change keeps the older cost until it does.
- Lab environment is not yet stood up. Containerlab plus an `snmpsim` fixture corpus is needed before WP-1.5. See `WORKFLOW.md` § Test data.
- `docker-compose.yml` is in the `CONVENTIONS.md` §1 layout and `ARCHITECTURE.md` §2 names Docker Compose as the deployment orchestrator, but no Phase 0 package creates it. It needs a package of its own, most naturally in Phase 8 alongside hardening.
- **`dotnet test` now needs a Docker daemon** for `NetShield.IntegrationTests` alone. WP-0.3 gave that project its first tests and the Testcontainers dependency `CONVENTIONS.md` §7 requires; unit and architecture tests stay container-free, so a layer can still be run on its own. The WP-0.2 "Done when" criteria — dashboard health, `/health`, `/health/ready`, and the `timescaledb` extension version — are still verified by hand rather than by a test, and the harness to automate them now exists.
- `WORK_PACKAGES.md` WP-0.2 names **MailHog**; the build uses **MailPit** (`axllent/mailpit:v1.31.0`) instead. MailHog was archived upstream in 2024 at v1.0.1. MailPit is the maintained drop-in with the same SMTP-sink and web-UI role, and it ships a `/readyz` endpoint that lets the dashboard report the resource healthy. The WP text has not been edited; this note is the record of the deviation.
- `ServiceDefaults.MapDefaultEndpoints` maps the health endpoints in the Development environment only, which is the Aspire template's default and the reason a `dotnet run` outside Aspire answers 404 there. A Docker Compose deployment will need container health checks against these paths, so the package that writes `docker-compose.yml` has to decide deliberately whether to expose them in production and on which interface.
- `NetShield.UnitTests` reaches the Postgres container's resolved environment through `GetEnvironmentVariableValuesAsync`, which Aspire 13.5.3 marks obsolete; its replacement, `ExecutionConfigurationBuilder`, is not public in that version. The call is behind a scoped `#pragma` in `AppHostModel`. Revisit when Aspire makes the replacement public.
- The AppHost pins `timescale/timescaledb:2.29.0-pg17` and `axllent/mailpit:v1.31.0` by literal; Redis floats on the Aspire default (8.6 today). Container image versions have no equivalent of `Directory.Packages.props` and nothing yet updates them.
- The `ARCHITECTURE.md` §4 module rules are enforced over the **project-reference graph**, not over loaded assemblies, because a reference an empty project declares is elided from assembly metadata and a reflection rule would pass over all ten modules vacuously. Two §4 rules are therefore still unenforced and need an assembly-level rule library (NetArchTest or ArchUnitNET) in WP-1.1, once a module holds real types: *cross-module communication carries `Contracts` types only*, and *no module exposes an EF entity across its boundary*.
- **Nothing applies migrations at run time.** WP-0.3 ships `Platform_AddOutbox`, WP-0.4 ships `Identity_AddUsersAndRefreshTokens` and WP-0.5 ships `Platform_AddAuditLog`, each applied explicitly in its integration-test harness; `Web.Host` does not migrate on startup, by decision. Until a migration step exists, a freshly started stack has none of those tables: the outbox dispatcher logs one error then backs off to a warning a minute, and the first-run seeder reports the missing `users` table and lets the host start rather than taking the API down with it — so **`aspire run` against an unmigrated database comes up healthy but has no administrator to sign in as, and every authentication endpoint answers 500.** WP-0.5 adds a third consequence: with no `audit_log` table the middleware logs one `Error` per state-changing call and the call itself still succeeds, so the API would run unaudited rather than refusing to. The manual migration step is in the WP-0.4 verification checklist. WP-1.1 is the first package that cannot proceed without settling this — a dedicated migration process or job, not a startup hook. Two contexts now need applying, so whatever settles it has to apply both.
- `IntegrationEventRegistry` keys an outbox row by the event type's `FullName`, so moving or renaming an event type is a breaking change for rows still in flight. Fine while nothing is deployed; revisit before the first release if event types look likely to move.
- The outbox dispatcher assumes it is the only one running — it claims rows with a plain query rather than `FOR UPDATE SKIP LOCKED`. Correct for the single-node V1 in `SPEC.md` §3, and the reason `AddOutboxDispatcher` is a separate opt-in call that only `Web.Host` makes. A second dispatching process would double-deliver.
- Delivered outbox rows are kept, and nothing prunes them. They belong in the retention policy table `ARCHITECTURE.md` §3 describes, which arrives with the policy work in Phase 8.
- `OutboxPayload` uses reflection-based `System.Text.Json` rather than a source-generated context. `CONVENTIONS.md` §4 requires source generation for the API's JSON; these rows are internal and never leave the process, but the choice would have to be revisited if a NetShield process were ever published trimmed or AOT.
- `.editorconfig` carries placeholder sections for `*.py` and `*.{ts,tsx,...}` ahead of the collector (WP-1.3) and the SPA (WP-0.6). Revisit them when those toolchains land — `ruff` and Prettier own formatting there, not `dotnet format`.
- `Directory.Packages.props` now sets `CentralPackageTransitivePinningEnabled`, which surfaced two existing transitive downgrades and moved `Microsoft.Extensions.Hosting` from 10.0.0 to 10.0.11 to clear them. Every EF Core package is pinned at 10.0.11 and the local `dotnet-ef` tool was updated to match; a future `aspire update` has to keep the two in step.
- **The audit row is written after the domain change commits, not with it.** The middleware records once the endpoint has answered, in its own transaction, which is what lets it record a 401 or a 403 the endpoint never saw. A process death in the window between the two loses the row. Accepted deliberately (see `DECISIONS.md`); if audit ever has to be atomic with the change it describes, the answer is to route it through the transactional outbox, not to hand-write an append into every handler.
- **`source_ip` is the socket's remote address, with no forwarded-headers handling.** Behind a reverse proxy — which is how a Docker Compose deployment will run — every audit row would name the proxy rather than the user. The package that writes `docker-compose.yml` has to configure `UseForwardedHeaders` with a trusted-proxy list, and it must be a list rather than "trust everything", or the field becomes attacker-controlled.
- **Deny-by-default now applies to every endpoint added from here on.** An endpoint with no policy answers 401. WP-0.6's SPA hosting is the first thing this will bite: `MapFallbackToFile` and the static-file routes have to declare `AllowAnonymous()`, or the sign-in page itself will require a session.
- **Nothing reads the audit log.** `Permission.AuditRead` is defined, granted to the Administrator, and unused — there is no query endpoint and no screen. The Administration screen in Phase 8 owns both, and will need cursor pagination and filters by actor, action, target and time.
- **Nothing prunes `audit_log`.** Like the delivered outbox rows, these belong in the retention policy table `ARCHITECTURE.md` §3 describes. Unlike the outbox rows, pruning them is a policy decision with a compliance edge to it, and the database rule refuses a `DELETE` — whatever prunes it will have to drop the trigger, delete, and restore it, deliberately and audibly.
- **The `must_change_password` claim can go stale in one direction.** It is minted at sign-in and re-minted on refresh and on the change that clears it. An administrator setting the flag on somebody else's account mid-session would not refuse that session until it refreshes. Nothing can set it today; whichever package adds administrator-initiated password reset has to decide whether a forced reset also revokes the target's sessions.
- **The permission set is defined but barely exercised.** Only the test project's probe endpoints call `RequirePermission`, because no module endpoint exists yet. Every package from WP-1.1 on has to declare a permission per endpoint, and the first few will show whether the grain is right — it is much cheaper to split a permission now than after a dozen endpoints name it.
- `AuditPayload` serialises before/after with reflection-based `System.Text.Json`, the same choice and the same caveat as `OutboxPayload`: internal, never leaves the process, would have to be revisited if a NetShield process were ever published trimmed or AOT.
- The audit snapshot member names avoid the words `SecretRedactor` treats as secret — `changeRequired` rather than `mustChangePassword`. It works and it is documented at both call sites, but it is a trap for the next author, who will name a field honestly and find `[REDACTED]` in the column. Worth a lint or a test that fails when a snapshot key is one the redactor would blank.
